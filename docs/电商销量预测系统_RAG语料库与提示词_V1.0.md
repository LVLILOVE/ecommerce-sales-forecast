## 0. 语料库设计与使用

### 0.1 语料块结构

### 0.4 分块原则（为什么这么切）

| 原则 | 说明 |
|---|---|
| **一块一个可独立回答的问题** | 例如"指标口径是什么"是独立一块；不要把"接口清单"和"错误码"混在一起 |
| **保留约束标记**（🔒/📌/⚠️） | 这些标记承载"能不能改"的信息，删掉后答案会失去力度 |
| **保留编号**（`BE-*` / `FR-*` / `F-*` / `T-*`） | 编号是溯源锚点，也是防幻觉的抓手 |
| **保留实测值**（⏱️） | 语料里写"性能良好"毫无价值；写"11.85 s"才能被追问 |
| **宁多勿碎** | 目标 150–600 字/块。过碎会让回答失去上下文，过大会稀释检索精度 |

### `RC-OVW-01` 项目是什么、要解决什么问题

- **主题**：项目概览
- **出处**：《项目任务书 V1.0.0》§1、§2
- **标签**：`项目背景` `目标` `ERP` `补货` `Web应用`

**项目定位**：电商与仓储场景下的**销量预测 Web 应用**。运营人员在浏览器上传历史销量 CSV，
系统自动完成预处理与特征工程，用 LSTM 预测未来若干天的销量，输出预测曲线与误差指标，
辅助补货计划与分仓规划。

**要解决的业务问题**：预测偏高造成库存积压与资金占用，预测偏低导致缺货与履约延误。
大促节奏叠加多仓库、多 SKU 的形态，使人工经验预估难以支撑精细化补货。

**总体目标**：开发一款基于 LSTM 的电商销量预测 Web 应用，用户无需掌握编程技能即可使用。

### `RC-ARC-05` 接口文档离线化（Swagger / ReDoc）

- **主题**：架构与部署
- **出处**：《开发技术文档 V1.0》§10.4、《部署运维手册 V1.0》§3.3
- **标签**：`Swagger` `ReDoc` `离线化` `CDN` `白屏`

`/docs`、`/redoc` 默认从 `cdn.jsdelivr.net` 加载 UI 资源。**国内受限网络下 CDN 被重置**，
症状是「HTML 拿到 200，但页面白屏、一个接口条目都渲染不出来」。

**做法**：随仓库自带 `swagger-ui-bundle.js`（v5.33.1）、`swagger-ui.css`、`favicon-32x32.png`、
`redoc.standalone.js`（v2.1.5），放在 `app/static/vendor/`，用自定义 `/docs`、`/redoc` 路由显式指向本地。

⚠️ **两处藏在默认参数里的外链**（只改主参数除不干净，EP-10 实测命中）：
① `get_redoc_html(..., redoc_favicon_url=...)` 默认指向 `https://fastapi.tiangolo.com/img/favicon.png`；
② `with_google_fonts=True` 会外链 Google Fonts。两者都必须显式关闭/改写。

**验收必须用真实浏览器**：`curl` 返 200 在缺陷存在时**同样是 200**。
判据是三条一起看：`.opblock` 数量 > 0、DOM 内零外部 `http(s)` 引用、`Network.loadingFailed` 为空。

### `RC-ALGO-01` 算法流程四阶段

- **主题**：算法
- **出处**：《项目任务书 V1.0.0》§3.3
- **标签**：`流程` `数据准备` `训练` `调参` `部署`

1. **数据准备**：使用菜鸟「需求预测与分仓规划」数据集（阿里天池 167097）。按时间先后
   **8:1:1** 划分训练/验证/测试集（避免未来信息泄漏）；缺失值线性插值；异常销量尖峰截断；
   滑动窗口切分扩充样本。
2. **模型训练**：多层 LSTM，损失 MSE，Adam 优化器 + 学习率衰减，验证集早停防过拟合。
3. **模型优化**：对窗口长度、隐藏层单元数、层数、dropout、学习率做网格搜索；
   以**移动平均基线**对比确认提升幅度。
4. **推理部署**：模型部署到服务端，通过 API 提供预测服务。

### `RC-ALGO-02` 五条必须保持的算法设计铁律

- **主题**：算法
- **出处**：项目实践（`app/algo/features.py`、`train.py`）；《测试报告 V1.0》§3.2
- **标签**：`铁律` `残差` `序列切分` `退化序列` `尖峰` `主指标口径`

1. **学残差，不学绝对值**：目标 = `(y − 移动平均基线)/σ`（`TARGET_RESIDUAL`）。
   学绝对值会让预测塌回序列均值（实测 预测std/真值std = 0.26）。
2. **按序列切分**（`split_by_series`），不按样本切 —— 同序列相邻两天近乎相同，按样本切**必然泄漏**。
3. **退化序列过滤**：`MIN_USABLE_SIGMA = 0.5`。σ≈0.03 的近常量序列除完后残差放大十倍，会污染全局 loss。
4. **营销节点保护**：`truncate_spikes(..., preserve_calendar=...)`。
   无条件截断会把双十一尖峰削掉，而那是**唯一可学的业务信号**。
5. **主指标只算 L1**：`levels_for_main=("L1",)`。L2 是规则的锅（实测 L2 MAPE ≈ 60%），
   混进来会把 13.6% 变成 25.9%。

### `RC-ALGO-03` 序列三级降级（L1 / L2 / L3）

- **主题**：算法
- **出处**：《PRD V1.0》`FR-MOD-05` / `FR-MOD-09`、《开发技术文档 V1.0》§4.5
- **标签**：`分级` `降级` `稀疏` `长尾` `L1` `L2` `L3`

| 级别 | 判定规则（`L1_MIN_VALID_POINTS = 90`） | 处理方式 |
|---|---|---|
| **L1** | 仓库 × 商品序列**有效历史 ≥ 90 天** | 走 LSTM 推理 |
| **L2** | 自身不足但**同商品跨仓聚合 ≥ 90 天** | 商品级降级 + 按各仓历史占比**分摊** |
| **L3** | 跨仓聚合仍 < 90 天 | 🔒 **不输出数值预测**，只给历史均值 |

**为什么 L2 用"跨仓聚合"**：真实数据是长尾 —— 天池菜鸟数据集 963 商品 × 5 仓 ≈ 4,815 条理论序列，
但存在 **17,063 条仓库缺失样本**，很多商品只在 1–2 个仓有货。跨仓聚合能显著提高可用序列数，
且分摊比例有真实依据（各仓历史占比）。

📌 **稀疏是常态，不是异常分支** —— 三级降级是**正常路径**。

### `RC-ALGO-05` 为什么不做在线重训练

- **主题**：算法
- **出处**：📌 已确认决策 `Q6`；《开发技术文档 V1.0》§4.7
- **标签**：`预训练` `SLA` `重训练` `决策`

### `RC-ALGO-06` 预处理与特征工程细节

- **主题**：算法
- **出处**：《开发技术文档 V1.0》§4.3、§4.4
- **标签**：`插值` `截断` `滑动窗口` `特征`

- **缺失值**：线性插值填补。
- **异常尖峰**：截断处理，但**保留营销日历节点**（见 `RC-ALGO-02` 第 4 条）。

### `RC-MET-01` 指标口径（必须按此口径回答）

- **主题**：数据与指标口径
- **出处**：📌 已确认决策 `Q2`；《PRD V1.0》§4
- **标签**：`口径` `加权MAPE` `WAPE` `达标序列占比` `基线`

📌 **主指标 = 销量加权 MAPE**，即 `Σ|e| / Σ|y|`（也称 WAPE）。
**辅指标 = 达标序列占比 ≥ 60%**。**基线 = 移动平均**。

**为什么用加权而非"每序列 MAPE 再平均"**：后者会让一条日销 3 件的小序列
与一条日销 300 件的大序列**权重相同**，指标失去业务意义。

**达标序列**：单序列 MAPE ≤ 20% 即视为达标。实测 83.95%（68/81）。

### `RC-MET-02` 数据集字段与校验规则

- **主题**：数据与指标口径
- **出处**：《开发技术文档 V1.0》§4.2、《PRD V1.0》`FR-UPL-*`
- **标签**：`字段` `校验` `七步` `仓库列`

**必需四列（英文列名，区分大小写）**：`sku_id` / `warehouse_id` / `date` / `sales`。

**七步顺序校验**：扩展名 → 文件大小 → 行数 → **表头完整性** → 日期可解析性 →
销量非负 → 时间连续性（断档）。

### `RC-DB-02` PRAGMA 四件套（🔒 每次连接执行）

- **主题**：数据库
- **出处**：《开发技术文档 V1.0》§3.9、《部署运维手册 V1.0》§4.3
- **标签**：`PRAGMA` `外键` `WAL` `BE-13`

```sql
PRAGMA foreign_keys = ON;      -- 🔒 SQLite 默认 OFF，不开启则外键完全失效（BE-13）
PRAGMA journal_mode = WAL;     -- 一写多读并发（NFR-REL-04）
PRAGMA busy_timeout = 5000;    -- 写锁等待 5 秒而非立即报错
PRAGMA synchronous = NORMAL;   -- WAL 下的推荐值，兼顾安全与性能
```

⚠️ `journal_mode=WAL` 是**库级、写一次持久生效**；而 `foreign_keys` / `busy_timeout`
是**连接级**的，每条新连接都要重设。

| `40001` | 缺少必需字段（缺列） | `40007` | 文件过大 |

### `RC-API-03` 三条接口设计红线

- **主题**：接口与契约
- **出处**：《开发技术文档 V1.0》§5、《项目开发实施方案》§9.1
- **标签**：`路由顺序` `幂等` `软失败`

1. 🔒 **路由注册顺序**（`BE-39`）：字面量路径必须排在参数化路径**之前**。
   `POST /history/compare` 与 `GET /history/dashboard` 必须排在 `GET|DELETE /history/{task_id}` 之前，
   否则 `compare` 会被当 `task_id` 吞掉（报 `40012`）。`datasets` 同理。
2. 🔒 **软失败不返 5xx**：超时返回 `E_TIMEOUT`、序列超限返回 `E_TOO_MANY_SERIES`，
   HTTP 仍是 200 + `code != 0`，并给 `completed_stage` 与三条建议。
   极限规模实测：1000 序列 × h=30 → `E_TIMEOUT`，**无半成品落盘**。
3. 🔒 **幂等**：`API-07`（示例数据加载）重复调用不产生重复数据集；
   `API-20`（软删除）二次调用返回相同结果，且 `predictions` + `metrics` **行数完全不变**。

### `RC-API-04` 契约一致性守卫

- **主题**：接口与契约
- **出处**：`scripts/verify_ep9_contract.py`
- **标签**：`契约` `双向` `MODEL_TO_TS` `漂移`

`verify_ep9_contract.py` 做**四组双向比对**：

| 组 | 比对对象 |
|---|---|
| A | 后端模型字段（`code/backend/schemas.py`）↔ 前端类型（`web/src/types/index.ts`） |
| B | 路由与调用点：OpenAPI `paths` ↔ `web/src/api/client.ts` |
| C | 枚举取值域：pydantic `Literal` ↔ TS 字面量联合类型 |
| D | 常量同源：后端模块常量 ↔ TS `LIMITS` / `THRESHOLDS` |

🔒 **核心机制**：`MODEL_TO_TS` 是一张**必须逐条登记的映射表**。两端任何一侧新增模型或接口
而不登记，脚本即失败 → 「忘了同步」在结构上**不可能静默通过**。

### `RC-SEC-01` 认证与会话

- **主题**：安全与权限
- **出处**：《开发技术文档 V1.0》§6
- **标签**：`JWT` `bcrypt` `限流` `token_version`

- 密码用 **bcrypt** 哈希（含 72 字节边界处理），数据库中**无明文密码**。
- **JWT** 有效期 720 分钟；`JWT_SECRET` 必须 ≥ 32 字符（`BE-05`）。
- 🔒 **`token_version`**：改密、重置密码、停用账号都会使 `token_version + 1`，
  **旧 Token 立即失效**。
- **登录限流**：连续失败 3 次锁定 60 秒（`LOGIN_MAX_FAIL` / `LOGIN_LOCK_SECONDS`）。
  ⚠️ 该实现是**进程内内存**，故 `--workers` 必须为 1（多进程会使限流失效）。
- **防枚举**：登录失败不区分"用户不存在"与"密码错误"。

|---|---|---|
| `data/exports/`（正式导出） | **7 天**（`EXPORT_TTL_DAYS`） | 用户可下载的导出产物 |
| `data/exports/tmp/`（错误明细临时文件） | **1 小时**（`EXPORT_TMP_TTL_SECONDS`） | ⚠️ **必须与正式导出分目录**，否则 7 天策略会误保留临时文件 |
| 游客数据（`user_id = 0`） | **24 小时**（`GUEST_DATA_TTL_HOURS`） | 优先清理 |

运维入口：`python scripts/cleanup_tmp.py --with-tmp --with-guest`（先加 `--dry-run` 预览）。

### `RC-PIT-01` 最易踩的坑之一：副作用被异常回滚

- **主题**：踩坑与排错
- **出处**：《项目开发实施方案 V1.0》附录（十八条坑 第 4 条）
- **标签**：`get_db` `rollback` `commit` `隐式`

🔴 **现象**：`services/` 里做完状态变更后 `raise BizError`，指望 `get_db` 提交 ——
但 `get_db` 的契约是"**异常 → rollback**"，变更**被回滚**。

**三次真实后果**：
- `EP-2`：登录限流**永不生效**（fail_count 每次归零）；
- `EP-4`：五类校验失败**一条记录都不落库**，`API-11` 的错误明细永远拿不到；
- `EP-5`：**超时软失败任务查不到**。

**防法**：需要保留的副作用**在抛错前显式 `db.commit()`**。
**判据**：这条缺陷**在单次请求的返回值上看不出来** —— 接口该报的错都报对了，
**只有再查一次库才露馅**（原话是"复现得了但查不到"）。

### `RC-PIT-02` 最易踩的坑之二：哨兵值

- **主题**：踩坑与排错
- **出处**：《项目开发实施方案 V1.0》附录（十八条坑 第 5 条）
- **标签**：`哨兵值` `限流` `datetime.min` `None`

🔴 用 `datetime.min` / `0` 之类的"哨兵时间"表示"未锁定" →
判断"是否已解锁"的 `remain <= 0` 会**同时命中"根本没锁"** → 误删正在累积的计数 →
**限流静默失效**（`EP-2` 实测）。

**防法**：「计数中」与「已锁定」必须用**不同的类型**表达（如 `None` vs `datetime`）。

### `RC-PIT-03` 最易踩的坑之三：正则扫源码不先剥注释

- **主题**：踩坑与排错
- **出处**：《项目开发实施方案 V1.0》附录（十八条坑 第 8 条）
- **标签**：`守卫` `注释` `AST` `噪音`

🔴 拿正则扫源码做"痕迹/字面量"守卫，却**不先剥注释** → 注释里写「已移除 `X`」反而被判违规
→ 守卫变成噪音 → 最后被人关掉。

**本项目连踩三次**（`EP-1`、`EP-3`、`EP-5`）。

**防法**：守卫一律**先剥 `//` 与 `/* */`** 再扫；**能用 AST 就别用正则**
（`EP-4` 已改用 `ast.walk` 取真实 import）。

### `RC-PIT-04` 环境类坑（换机器会重现不了，必须文档化）

- **主题**：踩坑与排错
- **出处**：《测试报告 V1.0》§3、《部署运维手册 V1.0》§11
- **标签**：`代理` `profile锁` `隐藏属性` `异步删除`

| 坑 | 症状 | 防法 |
|---|---|---|
| 系统设了 `HTTP_PROXY` | 浏览器把 `127.0.0.1` 也塞进代理 → 本地页面全白/502 | 浏览器加 `--no-proxy-server` + `--proxy-bypass-list=<-loopback>` |
| vite 默认只监听 `[::1]` | 代理连不上 → 502 | 显式 `--host 127.0.0.1` |
| vite 代理写死端口 | 用独立临时库跑测试时，前端能开但**每个接口都失败**，后端日志无请求 | 改读 `VITE_API_TARGET` 环境变量 |
| 复用固定 `--user-data-dir` + 只 kill 父进程 | 子进程持有 profile 锁 → 新实例**静默挂起**：不报错、不产截图、空转 15 分钟 | ① 每次全新 profile；② 杀**进程树**；③ 单次截图套超时 |
| `taskkill` 异步，紧接着删 profile | 文件锁未释放 → 删除静默失败 → **永久残留 1.65 GB** | 删除前等待 + 重试 + 失败显式告警 |
| 平台把 `rmSync` 转成异步移入回收站 | "删完立刻查"**误判成清理失败**（1 分钟后为 0） | 验收清理必须**隔一会儿再统计** |
| Chromium profile 是**隐藏属性** | `Get-ChildItem` 默认不返回 → 计数偏小 → 误判"删干净了" | 统计加 `-Force` |

⚠️ **教训**：「删除失败」与「删除成功但看不出来」是**两种截然不同的故障**，
而它们的表现都是「文件还在」。

## 2. 用于构建 RAG 助手的提示词

### 2.1 系统提示词（RAG 助手人设与边界）

```text
你是「电商销量预测系统」的项目答疑助手。你的唯一知识来源是检索到的语料块。

【回答规则】
1. 只依据检索结果回答。若检索结果不足以回答，直接说「现有资料未涵盖此问题」，
   并指出最接近的语料块编号。**不得凭常识推测或编造。**
2. 每个关键结论后必须标注来源编号，格式：`（见 RC-XXX-NN）`。
3. 遇到带 🔒 的内容，必须原样保留该标记并说明「这是硬约束，改动会破坏验收」。
   遇到 📌 说明「这是已确认决策，不再讨论」。
4. 遇到具体数值（MAPE / 耗时 / 参数），必须**原样引用实测值**，
   禁止改写成「较好」「很快」这类模糊表述。
5. 若用户问的是「能不能改 X」：
   - 先查是否有 🔒 / 📌 标记；
   - 有则回答「不建议/不可以改动，原因是……」并给出依据编号；
   - 无则给出改动影响面（会牵连哪些模块、哪些校验脚本会失败）。
6. 若用户的问题涉及**其他项目或通用知识**（与本项目无关），礼貌说明本助手只回答本项目相关问题。
7. 不确定的事，明确说「不确定」。**宁可少答，不可错答。**

【语气】简洁、技术化、直接给结论。不要客套开场白，不要说「很好的问题」。
【语言】简体中文。
```

### 2.2 检索提示词（查询改写 / 扩展）

RAG 的第一道关口是**召回**。用户的自然语言提问往往与语料措辞不重合，
故在检索前做一次改写，用 LLM 产出多个检索式：

```text
你是检索查询改写器。用户会用日常语言提问，但知识库使用技术术语。
请把用户问题改写成 3–5 条**不同角度**的检索查询，以提高召回率。

要求：
1. 覆盖：① 术语化改写（用项目里的正式说法）② 同义词/别名 ③ 若涉及编号，
   直接给出可能的编号前缀（如 BE-、FR-、RC-）；
2. 每条查询独立、简短（≤ 20 字），不要句子；
3. 只输出 JSON 数组，不要解释。

示例：
用户问题：「预测准不准？」
输出：["加权 MAPE 实测值","MAE RMSE 相对移动平均基线 降低幅度",
      "达标序列占比","技术指标 验收标准","RC-MET-01"]

用户问题：
"""
{question}
"""
```

**推荐检索配置**（本项目语料规模下足够）：

| 项 | 建议 |
|---|---|
| 召回方式 | **混合检索**：BM25（`tags` + 标题）与向量检索各取 top-8，合并去重 |
| 元数据过滤 | 先按 `topic` 过滤（若问题明确指向某主题，如"性能"）→ 再检索 |
| 重排 | 用 `tags` 命中数 + 向量相似度加权（简单有效） |
| 上下文 | 取 top-4 块，按 `id` 升序拼接（保持主题连贯） |

### 2.3 回答生成提示词（带引用）

```text
请基于以下检索结果回答用户问题。

【检索结果】
{context}

【用户问题】
{question}

【输出格式】
- 先用一句话给结论；
- 再用 2–5 条要点展开，每条要点末尾标注来源 `（见 RC-XXX-NN）`；
- 若涉及代码/命令/配置，用代码块原样给出；
- 若检索结果中有 🔒 或 📌 标记，必须保留标记并说明其含义；
- 若检索结果不足以回答，输出：「现有资料未涵盖此问题。最接近的是 RC-XXX-NN，
  它讲的是……」，不要编造。
```

### 2.4 评测提示词（RAG 质量自检）

RAG 系统本身也需要被评测，否则无法判断"答得对不对"。以下三组用于自动化评测：

**① 忠实度（有没有编）**

```text
判断「回答」中的每一条事实性陈述是否都能在「检索结果」中找到依据。

【检索结果】{context}
【回答】{answer}

输出 JSON：
{"total": <陈述总数>, "supported": <有依据条数>,
 "unsupported": [{"claim": "……", "why": "检索结果中无此内容"}]}

判定标准：
- 数值必须逐位一致（14.26% ≠ 约 14%）；
- 编码必须一致（BE-13 ≠ BE-15）；
- 「推测/推断」的表述也算无依据。
```

**② 检索相关性（召回得对不对）**

```text
给定用户问题和检索到的 4 个语料块，判断每个块与问题的相关性。

【问题】{question}
【语料块】{chunks}   （每条含 id / topic / tags / 正文）

对每个块输出 0–2 分：
  2 = 直接回答该问题
  1 = 提供背景，但不直接回答
  0 = 无关

输出 JSON 数组：{"id": "RC-XXX-NN", "score": 2, "why": "……"}
```

**③ 答案完整性（该说的说了没）**

```text
给定用户问题、标准答案要点、以及 RAG 的回答，判断要点覆盖率。

【问题】{question}
【应覆盖要点】{gold_points}
【RAG 回答】{answer}

输出 JSON：
{"covered": ["要点1", "要点2"], "missed": ["要点3"],
 "coverage_rate": 0.67, "note": "遗漏的要点是否影响可用性"}

```

### 2.5 一组"必须答对"的验收问题（golden set）

用于回归 RAG 质量。以下每个问题都应能由语料库正确回答：

| # | 问题 | 期望命中的语料块 | 关键判据 |
|---|---|---|---|
| 1 | 为什么不做在线重训练？ | `RC-ALGO-05` | 必须说明**理由是 SLA 而非显存**，并给出 111 MB 实测 |
| 2 | 预测粒度是什么？为什么仓库列缺失要拒？ | `RC-MET-02` | 必须答「仓库 × 商品」，且说明"错了看不出来" |
| 3 | 指标口径是加权 MAPE 还是平均 MAPE？ | `RC-MET-01` | 必须答 WAPE 及其理由 |
| 4 | L2 序列的判定规则是什么？ | `RC-ALGO-03` | 必须提到**跨仓聚合 ≥ 90 天** |
| 5 | 关键坑：为什么接口报错了但库里没记录？ | `RC-PIT-01` | 必须提到 `get_db` 异常回滚 + 显式 commit |
| 6 | 前端能开但所有接口都失败，后端日志没请求，为什么？ | `RC-PIT-04` | 必须提到 vite 代理端口写死 / `VITE_API_TARGET` |
| 7 | 为什么数据隔离红线只能在 `admin.py` 例外？ | `RC-SEC-02` | 必须提到 AST 扫描 + `CurrentAdmin` + 全审计 |
| 8 | `/docs` 白屏但返回 200，怎么排查？ | `RC-ARC-05` | 必须提到 CDN 被墙 + 三条判据 |

### 2.6 常见的 RAG 失败模式（本项目语料下要特别注意）

| 失败模式 | 症状 | 缓解 |
|---|---|---|
| **数值被"约化"** | 把 14.26% 答成"约 14%" | 系统提示词第 4 条 + 忠实度评测 |
| **约束标记被丢掉** | 把 🔒 硬约束答成"建议" | 系统提示词第 3 条；语料块保留标记 |
| **跨块混淆** | 把 `BE-05`（密钥）与 `BE-13`（外键）搞混 | 检索后按 `id` 升序拼接 + 忠实度评测查编号 |
| **答了"通用最佳实践"** | 不问项目，直接讲"一般推荐用 Redis" | 系统提示词第 6 条（只答本项目） |
| **过度自信** | 检索为空仍编出答案 | 系统提示词第 1 条 + 第 7 条（宁可少答） |

## 3. 语料库的可复现性与自检

```bash
python scripts/build_rag_corpus.py           # 抽取 → outputs/电商销量预测系统_rag_corpus.json/.jsonl
python scripts/build_rag_corpus.py --check   # 自检：块数 / id 唯一 / 元数据齐备 / 标签非空
```

**自检项**：① 块数 ≥ 40；② `id` 全局唯一且符合 `RC-<主题>-<序号>` 格式；
③ 每块 `topic` / `source` / `tags` / `text` 均非空；④ `topic` 取值在白名单内；
⑤ 正文长度在 80–2000 字之间（过短无信息量、过长稀释检索精度）。
