## 1. 系统概览

### 1.1 架构

前后端分离的 B/S 架构，单机部署：

```
                    ┌──────────────────────────────────────────┐
   浏览器 ──────────►│  Nginx（生产，:80）                       │
  （Chrome/Edge/     │   ├─ /            → web/dist 静态文件     │
   Firefox）         │   ├─ /api/ + /health + /docs + /redoc     │
                    │   │              → 127.0.0.1:8000 (FastAPI)│
                    │   └─ /static/vendor/*（Swagger 离线资源）  │
                    └──────────────────────────────────────────┘
                                     │
                    ┌────────────────▼─────────────────────────┐
                    │  FastAPI + uvicorn（:8000）               │
                    │   ├─ 算法层 app/algo/（LSTM 推理，单例）   │
                    │   ├─ SQLite data/app.db（WAL 模式）       │
                    │   └─ 文件：data/uploads / data/exports    │
                    └──────────────────────────────────────────┘
```

**开发态**（不经过 Nginx）由 Vite dev server（:5173）把 `/api`、`/health` 代理到后端 `:8000`。

### 1.4 运行期硬约束（写进验收红线）

| 编号 | 约束 | 违反后果 |
|---|---|---|
| 🔒 `BE-05` | `JWT_SECRET` 缺失或 < 32 字符 → **启动直接失败** | 若容错放行，任何人拿公开默认密钥即可伪造 Token |
| 🔒 `BE-13` | 每次连接必须 `PRAGMA foreign_keys = ON` | SQLite 默认关闭外键，删主记录不留孤儿、外键形同虚设 |
| 🔒 `BE-15` | 启动时预加载模型，失败即启动失败 | 否则「服务正常、接口 200，但每次预测都用错版本」的静默故障 |
| 🔒 `GIT-7` | 改算法参数后**必须**重跑训练与评估脚本 | 界面数字会落后于模型（本项目出现过「两套数字」） |
| 📌 `QD-06` | 首页硬指标从 `outputs/eval_report.json` 构建期注入 | 禁止手写，防「两套数字」复发 |
| 📌 训练时机 | **纯预训练推理**，不提供在线重训 | 端到端 SLA 60 s 内无法稳定容纳「训练+调参+早停」 |

## 2. 环境准备

### 2.1 硬件最低配置

| 项 | 最低 | 推荐 | 说明 |
|---|---|---|---|
| CPU | 2 核 | 4 核+ | 无 GPU 时走 CPU 推理 ⏱️ 实测 h=14 端到端 23.5 s |
| 内存 | 4 GB | 8 GB+ | ⏱️ 实测峰值常驻 < 1 GB（模型仅 31,729 参数） |
| 磁盘 | 2 GB 可用 | 10 GB+ | 模型 128 KB；数据库与上传文件按业务增长 |
| GPU（可选） | —— | 支持 CUDA 的任意显卡 | ⏱️ 显存占用峰值仅 **111 MB**，2 GB 的老卡也够 |

> ⚠️ **别以为 LSTM 很吃显存**。本模型 hidden=48、2 层，参数量 31,729，⏱️ 训练 100k 样本时
> 峰值显存实测 111 MB。**1 分钟 SLA 之所以排除在线训练，理由是「训练+网格调参+早停
> 无法稳定塞进 60 秒」，不是因为显存不够** —— 这个区别在答辩时会被追问。

```bash

# Windows: .venv\Scripts\activate

# ① 先装普通依赖
```

> ⚠️ **国内网络**：`download.pytorch.org` 可能不可达。替代方案：
> ① 使用国内镜像（如阿里云 PyPI 镜像装 CPU 版 + 单独下 CUDA wheel）；
> ② 无 GPU 机器**直接装 CPU 版**即可 —— 算法层有设备自动回退（`FR-MOD-10`），
> 配置 `TORCH_DEVICE=cpu` 或 `auto` 都会正常工作，只是慢一些（⏱️ 23.5 s vs 11.9 s）。
>
> ⚠️ 安装完成后**必须验证**，别只看 `pip list`：
> ```bash
> python -c "import torch; print(torch.__version__, torch.cuda.is_available())"
> # 期望：2.9.1+cu128 True   （CPU 机器得到 2.9.1+cpu False 也是正常的）
> ```

### 3.2 首次部署（开发/联调态，3 条命令）

```bash
# ① 后端（自动建库建表 + 建种子数据 + 预加载模型）
python -m uvicorn app.main:app --host 127.0.0.1 --port 8000

# ② 前端 dev server（另开一个终端）
cd web && npm install && npm run dev

# ③ 验证
curl http://127.0.0.1:8000/health     # {"code":0,...,"data":{"status":"ok",...}}
# 浏览器打开 http://localhost:5173
```

> ⚠️ 首次启动会执行 `init_db(run_seed=True)`：建表、建视图、建触发器、**补游客哨兵账号
> （`users.id = 0`）与管理员种子账号**。全过程幂等，重复启动无副作用。
>
> ⚠️ 启动若报 `JWT_SECRET 未配置或长度不足 32 字符` —— 这是 `BE-05` 的**预期行为**，

### 3.3 接口文档（`/docs`、`/redoc`）—— 🔒 资源已离线化

| 地址 | 内容 |
|---|---|
| `/docs` | Swagger UI，可在线调试 |
| `/redoc` | ReDoc，三栏阅读视图 |
| `/openapi.json` | OpenAPI 3.1 契约（机器可读） |
| `outputs/电商销量预测系统_API接口文档_V1.0.html` | **单文件离线归档件**，双击可开，零外链 |
| `outputs/电商销量预测系统_openapi.json` | 契约归档（可导入 Apifox / Postman） |

**为什么要自带资源**：FastAPI 默认从 `cdn.jsdelivr.net` 加载 Swagger UI 的 JS/CSS。
国内受限网络下 CDN 被重置，症状是「HTML 拿到 200，但页面白屏、一个接口条目都渲染不出来」。
🔒 因此本项目把 `swagger-ui-bundle.js`、`swagger-ui.css`、favicon、`redoc.standalone.js`
随仓库自带（`app/static/vendor/`），并用自定义路由显式指向本地路径。

> ⚠️ 两处**藏在默认参数里的外链**，只改主参数除不干净（EP-10 实测命中）：
> ① `get_redoc_html(..., redoc_favicon_url=...)` —— 默认 favicon 指向
> `https://fastapi.tiangolo.com/img/favicon.png`；② `with_google_fonts=True` 会外链 Google Fonts。
> 本项目两者都已显式关闭/改写，并由 `scripts/verify_docs_browser.mjs` 逐条断言。

**验证方式（🔒 必须用真实浏览器，`curl` 返 200 什么都不证明）**：

```bash
node scripts/verify_docs_browser.mjs           # Edge
BROWSER=chrome node scripts/verify_docs_browser.mjs
```

三条判据缺一不可：① `.opblock` 数量 > 0（真的渲染了）；② DOM 内零外部 `http(s)` 引用；
③ `Network.loadingFailed` 为空且无 4xx/5xx。当前状态：Edge / Chrome 各 **16/16 通过**。

### 3.4 生产构建与 Nginx

```bash
# ① 构建前端（tsc 类型检查 + vite build，产物在 web/dist/）
cd web
npm ci
VITE_API_TARGET=http://127.0.0.1:8000 npm run build     # 生产构建不需要该变量
cd ..

# ② 后端以生产模式启动（建议交给 systemd，见 §6.2）
APP_ENV=production python -m uvicorn app.main:app \
    --host 127.0.0.1 --port 8000 --workers 1
```

> 🔒 **`--workers` 必须是 1**。原因：登录限流的失败计数与黑名单是**进程内内存**实现
> （`TQ-2` 未引入 Redis）。多 worker 会让每个进程各持一份计数，限流形同虚设。
> 若将来确实需要多进程，**必须先把限流升级为共享存储**（Redis），这不是可以省略的前提。

**Nginx 站点配置**（`/etc/nginx/conf.d/sales-forecast.conf`）：

```nginx
server {
    listen 80;
    server_name _;                      # 生产替换为真实域名
    client_max_body_size 25m;           # 🔒 必须大于 MAX_FILE_SIZE_MB(20)，留出表单开销

    # 前端静态资源（SPA 兜底）
    root /srv/sales-forecast/web/dist;
    index index.html;

    # 带 hash 的构建产物可长缓存
    location /assets/ {
        expires 30d;
        add_header Cache-Control "public, immutable";
    }

    # 🔒 index.html 绝不缓存，否则发版后用户拿到旧壳、找不到新 chunk
    location = /index.html {
        add_header Cache-Control "no-store, must-revalidate";
    }

    # 后端 API
    location /api/ {
        proxy_pass http://127.0.0.1:8000;
        proxy_http_version 1.1;
        proxy_set_header Host              $host;
        proxy_set_header X-Real-IP         $remote_addr;
        proxy_set_header X-Forwarded-For   $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
        proxy_read_timeout 90s;         # 🔒 必须 > TASK_BUDGET_MS(60s)，否则长任务被 Nginx 掐断
    }

    location /health { proxy_pass http://127.0.0.1:8000; }

    # 🔒 接口文档与离线资源（Swagger/ReDoc 自带资源，不经 CDN）
    location /docs        { proxy_pass http://127.0.0.1:8000; }
    location /redoc       { proxy_pass http://127.0.0.1:8000; }
    location /openapi.json{ proxy_pass http://127.0.0.1:8000; }
    location /static/     { proxy_pass http://127.0.0.1:8000; }

    # SPA 兜底：非上述前缀一律回 index.html
    location / {
        try_files $uri $uri/ /index.html;
    }

    gzip on;
    gzip_types text/css application/javascript application/json image/svg+xml;
    gzip_min_length 1024;
}
```

```bash
sudo nginx -t && sudo systemctl reload nginx
```

> ⚠️ `proxy_read_timeout` 默认 60 s。若与 `TASK_BUDGET_MS=60000` 相等，边界上会来回打转：
> ⏱️ 实测 3 任务并发时单个任务最长 37.6 s，仍在 60 s 内，但**极限规模压力用例（1000 序列 ×
> horizon=30）后端要 250 s 才给出 `E_TIMEOUT`** —— 那种情况就是 Nginx 先掐断连接。
> 本项目的处理是**如实登记为「软失败路径」**（`P1-02`），生产若确有超大规模需求，
> 应把该接口改为异步 + 轮询，而不是把超时无限拉长。

### 4.2 日志

| 日志 | 位置 / 方式 | 内容 |
|---|---|---|
| 访问日志 | stdout（`AccessLogMiddleware`） | `[request_id] 方法 路径 状态码 耗时` |
| 应用日志 | stdout（`configure_logging`） | 启动自检、模型加载、业务异常 |

> 不要去猜时间点。

### 4.3 数据库参数（`app/core/db.py`，🔒 每次连接执行）

```sql
PRAGMA foreign_keys = ON;      -- 🔒 SQLite 默认 OFF，不开启则外键完全失效（BE-13）
PRAGMA journal_mode = WAL;     -- 一写多读并发（NFR-REL-04）
PRAGMA busy_timeout = 5000;    -- 写锁等待 5 秒而非立即报错
PRAGMA synchronous = NORMAL;   -- WAL 下的推荐值，兼顾安全与性能
```

> ⚠️ **`PRAGMA journal_mode=WAL` 是「写一次、持久生效」的库级设置**；
> 而 `foreign_keys` / `busy_timeout` 是**连接级**的，每条新连接都要重设 ——
> 这就是为什么它们写在连接工厂里，而不是建库时执行一次。

### 4.4 安全配置（生产必查）

| 项 | 建议 | 说明 |
|---|---|---|
| `JWT_SECRET` | 48 字符随机串，**仅存于服务端** | 泄露 = 任何人可伪造任意用户 Token |
| `APP_ENV` | `production` | 生产态不应把内部异常栈返回给前端 |
| `CORS_ORIGINS` | 生产**留空或填真实域名** | 同源反代下浏览器不会发跨域请求 |
| HTTPS | **必须**（`6.2` 数据隐私要求） | 用 Nginx + 证书；`X-Forwarded-Proto` 已透传 |
| 限流 | 保持 `LOGIN_MAX_FAIL=3` / `LOCK=60s` | ⚠️ 该实现是进程内内存，**必须单 worker** |
| 文件上传 | `client_max_body_size` > `MAX_FILE_SIZE_MB` | 两处不一致会出现「前端能选、Nginx 先 413」 |
| 目录权限 | `data/`、`.env` 仅服务账号可读写 | `chmod 600 .env` |

### 5.3 模型切换（管理端）

1. 操作在一个事务内：`deactivate_all()` → `activate_version()`，**中间不得提前 commit**（`BE-ADM-02`）；
2. 切换后热重载：`reload_active_model()`，并校验 `.env` 的 `ACTIVE_MODEL` 与实际启用版本是否一致（`BE-ADM-03`）；

## 7. 数据备份与恢复

### 7.1 备份（🔒 SQLite 必须用 `.backup`，不可直接 `cp`）

```bash
# ❌ 错误：WAL 模式下直接复制 .db，可能拿到缺 WAL 内容的不一致快照
# ✅ 正确：用 SQLite 的在线备份，自动处理 WAL
sqlite3 data/app.db ".backup 'backup/app-$(date +%F-%H%M).db'"

# 完整性校验（每次备份后都做）
sqlite3 backup/app-2026-10-13-0900.db "PRAGMA integrity_check;"   # 期望 ok
```

**推荐：用仓库自带脚本（免手工、自带轮转与自检）**

上面的手工步骤在实际运维里往往「不会被执行」，因此提供 `scripts/backup_db.py`：

```bash
python scripts/backup_db.py                 # data/app.db → backups/，保留 7 份
python scripts/backup_db.py --keep 30       # 保留 30 份
python scripts/backup_db.py --dry-run       # 只打印计划，不写盘
python scripts/backup_db.py --db data/app.db --out-dir /data/backup
```

它做四件事：① 用 `sqlite3.Connection.backup()` 在线复制（**WAL 下正确合并，无需停服务**）；
② 按份数轮转；③ 对备份文件跑 `integrity_check` **并与源库逐表比对行数**（备份「存在」≠「可用」）；
④ 输出一行摘要，便于重定向进日志。

定时执行：

```bash
# Linux cron：每天 03:00
0 3 * * * cd /opt/sales-forecast && python scripts/backup_db.py >> logs/backup.log 2>&1
```

Windows 用「任务计划程序」：程序 `python`，参数 `scripts/backup_db.py`，起始于项目根目录。

> ⚠️ 两个实测坑（脚本已内置处理，手工做时要注意）：
> ① 备份库会继承源库的 `journal_mode=WAL`，读一次就生成 `-wal`/`-shm` 伴生文件，
> 既污染备份目录又会让轮转漏删（脚本备份后切 `DELETE` 模式并清理伴生文件）；
> ② Windows 上「刚关闭连接立刻删」经常失败（句柄释放有延迟），轮转需带重试，
> 否则日志说清理了、文件还在。

**完整备份集应包含**：

| 对象 | 备份必要性 |
|---|---|
| `data/app.db` | 🔒 必需（用户/数据集/任务/预测/指标/模型注册/审计/埋点） |
| `outputs/models/` | 🔒 必需（模型权重 + 报告 + 示例数据） |
| `outputs/eval_report.json` | 🔒 必需（首页指标来源） |
| `data/uploads/` | 可选（原始 CSV 体量大，可用数据集元信息重建提示） |
| `.env` | 🔒 必需（含 `JWT_SECRET`，丢失后所有已发 Token 失效） |

### 7.2 恢复

```bash

rm -f data/app.db-wal data/app.db-shm        # 🔒 必须删掉旧 WAL/SHM，否则与恢复的库不匹配
```

### 9.2 回归执行纪律（⚠️ 血泪教训）

**每个校验脚本单独占一条命令执行，不要用 `for` 循环串跑。**

原因：平台的批量删除保护按**单次调用的累计删除数**计数（阈值 50）。
多个脚本各自清理自己的临时目录，串跑会让删除量累加到同一次调用上 → 被判为批量删除 →
后续脚本直接退出，日志只留一行 `STATUS: FAILED`。EP-9 首轮就因此出现三个脚本「假失败」。

## 11. 故障排查速查

### 11.1 启动失败

| 现象 | 根因 | 处置 |
|---|---|---|
| `JWT_SECRET 未配置或长度不足 32 字符` | `BE-05` 预期保护 | 在 `.env` 补 ≥ 32 字符随机串 |
| `model_registry 中没有启用记录` | 库没建好或种子未跑 | 确认 `init_db` 成功；或 `ACTIVE_MODEL` 与库不一致 |
| `配置漂移：.env 与库中启用版本不一致` | `BE-06` 预期保护 | 把 `ACTIVE_MODEL` 改成库里的启用版本（或反之） |
| `Address already in use` / `[Errno 10048]` | 上一个进程未退 | 按端口找 PID 杀掉再启（Windows：`netstat -ano \| grep :8000`） |
| `no such table: v_task_summary` | 用了 `create_all` 而非 `schema.sql` | 🔒 必须执行 `code/db/schema.sql`（视图/触发器/哨兵行只在那里） |

### 11.2 接口异常

| 现象 | 根因 | 处置 |
|---|---|---|
| 所有预测接口 `40404` | 模型单例未加载 | 看启动日志；`TestClient` 场景还须**全程同一 lifespan** |
| 上传接口报错但库里没记录 | 状态变更后 `raise BizError`，被 `get_db` 回滚 | 🔒 需要保留的副作用**在抛错前显式 `db.commit()`** |
| 登录限流永不生效 | 用哨兵时间（`datetime.min`/`0`）表示「未锁定」 | 🔒 「计数中」用 `None`、「已锁定」用 `datetime`，必须不同类型 |
| 历史对比把 `compare` 当 `task_id` | 路由注册顺序错误 | 🔒 `POST /history/compare` 必须排在 `/{task_id}` 之前（`BE-39`） |
| 非管理员访问管理端返回 403 而非 401 | 两种拒绝混用 | 未登录 → `401`；已登录无权限 → `40301` |

### 11.3 前端异常

| 现象 | 根因 | 处置 |
|---|---|---|
| 页面能开但**每个接口都失败**、后端日志无请求 | Vite 代理指向错误端口 | 设 `VITE_API_TARGET`（默认写死 8000） |
| 页面全白、控制台无报错 | 浏览器继承了系统代理，本地地址被塞进代理 → 502 | 浏览器加 `--no-proxy-server`；或清掉 `HTTP_PROXY` |
| `/docs` 白屏但返回 200 | Swagger 资源走 CDN 被墙 | 🔒 确认 `app/static/vendor/swagger-ui/` 资源存在 |
| `/redoc` 控制台出现 `fastapi.tiangolo.com` 请求 | 默认 favicon 未改写 | 传 `redoc_favicon_url`（⚠️ 不是 `favicon_url`） |
| 首屏偶发取不到 FCP 样本 | `goto` 后 settle 太短，React 还没画 | 读取加重试，**不要**放宽断言为 `n ≥ 2` |
| 断网环境下页面空白 | 前端引用了外部字体/图标 | 本项目前端**零外链**；若新增依赖须复查 |

### 11.4 数据异常

| 现象 | 根因 | 处置 |
|---|---|---|
| 删除主记录后出现孤儿行 | 外键未开启 | 🔒 每次连接 `PRAGMA foreign_keys = ON`（`BE-13`） |
| 恢复备份后行为怪异 | 旧 WAL/SHM 残留 | 恢复时同步删除 `app.db-wal` / `app.db-shm` |
| 指标显示与算法不一致 | 忘了跑 `sync_eval_metrics.py` | 🔒 `GIT-7`：重训后必须重跑注入脚本 |
| 数据库文件损坏 | 直接 `cp` 备份导致快照不一致 | 改用 `sqlite3 .backup` |

## 12. 升级与回滚

### 12.1 升级流程

```bash
# ① 备份（🔒 不可省）
sqlite3 data/app.db ".backup 'backup/pre-upgrade-$(date +%F-%H%M).db'"
tar czf backup/pre-upgrade-models-$(date +%F).tgz outputs/models outputs/eval_report.json

# ② 停服
sudo systemctl stop sales-forecast

# ③ 取新代码 + 装依赖
git pull
pip install -r requirements.txt
cd web && npm ci && npm run build && cd ..

# ④ 迁移（若有 schema 变更）
python scripts/migrate_0001_ch01_role.py

# ⑤ 回归
python scripts/self_check.py
python scripts/verify_ep10_docs.py

# ⑥ 起服 + 自检
sudo systemctl start sales-forecast
curl -s http://127.0.0.1:8000/health
```

### 12.2 回滚

```bash
sudo systemctl stop sales-forecast
git checkout <上一个正常版本 tag>
cp backup/pre-upgrade-<时间>.db data/app.db
rm -f data/app.db-wal data/app.db-shm
tar xzf backup/pre-upgrade-models-<日期>.tgz
cd web && npm ci && npm run build && cd ..
sudo systemctl start sales-forecast
```

> ⚠️ 回滚数据库是**破坏性操作**：升级后产生的所有业务数据都会丢失。
> 仅在升级后确认数据不可用时执行，且执行前**再备份一次当前库**留证。
