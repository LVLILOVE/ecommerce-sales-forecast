## 1. 建设目标与范围界定

### 1.1 「前台」与「后台」的准确定义（澄清）

需求原文写的是「前台展示企业官网系统 + 后台管理系统」。经与负责人确认，**这两个词在现有文档中的准确对应关系如下**（📌 决策 1）：

```
┌───────────────────────── 前台（未登录可见）─────────────────────────┐
│  UX-P01 产品首页（模板 D 营销页）   价值主张 / 硬指标 / 五步流程     │
│  UX-P02 登录                        邮箱密码 + 限流冷却              │
│  UX-P03 注册                        密码强度实时校验                 │
└───────────────────────────────┬─────────────────────────────────────┘
                                │ 登录成功 / 游客直通
                                ▼
┌───────────────────────── 后台（登录后）─────────────────────────────┐
│  UX-P04 工作台        概览 + 快速入口 + 最近任务                     │
│  UX-P05 上传数据 ─┐                                                  │
│  UX-P06 参数配置  ├─ 主流程 4 步（≤ 5 步硬约束 NFR-USE-01）          │
│  UX-P07 执行进度  │                                                  │
│  UX-P08 预测结果 ★┘ 核心交付页                                       │
│  UX-P09 历史任务 ─┐                                                  │
│  UX-P10 任务详情  ├─ 记录类                                          │
│  UX-P11 跨任务对比┘                                                  │
│  AD-P01 运营看板      ┐                                              │
│  AD-P02 用户与任务管理┘ ─ CH-01 新增（仅 role='admin' 可见）          │
└──────────────────────────────────────────────────────────────────────┘
```

**关键口径（避免歧义）**：

| 说法 | 准确含义 | 依据 |
|---|---|---|
| 「前台企业官网」 | **`UX-P01` 产品首页**——单页营销落地页，讲价值主张、硬指标、五步流程、数据集字段说明。**不是**多页面企业站（无公司介绍 / 新闻 / 招聘等页面） | UI/UX §6.1、§7.1；模板 D |
| 「后台管理系统」 | **登录后的 8 个业务页**（`UX-P04`~`UX-P11`），即「工作台 + 预测主流程 + 记录」。**不是**传统意义的运维后台 | UI/UX §6.1、§6.4 模板 A |
| 「管理端」（`CH-01` 新增） | 上述后台之上的**管理员专属页面**（`AD-P01`/`AD-P02`），仅 `role='admin'` 可见 | 本文档 §5 |
| 三者关系 | 前台 ⊂ 统一前端工程，后台 ⊂ 统一前端工程，管理端 ⊂ 统一前端工程。**同一个 React 工程、同一套设计令牌、同一套接口基址** | §3.2 |

> 📌 全站页面归为 **4 种模板**（A 应用页 / B 主内容+右栏 / C 认证页 / D 营销页），管理端两页**复用模板 A**，不引入新的视觉语言（`QD-01`、`RG-11`）。

### 5.3 数据库变更（⏱️ 已全部实测验证，不是纸面结论）

#### 5.3.1 变更一：`users` 增 `role` 列

**DDL（同步写入 `code/db/schema.sql`，位置紧接 `status` 之后）**：

```sql
    role            TEXT    NOT NULL DEFAULT 'user'         -- 角色：user 普通用户 / admin 管理员（CH-01）
                    CHECK (role IN ('user', 'admin')),
```

**存量库迁移语句**：

```sql
ALTER TABLE users ADD COLUMN role TEXT NOT NULL DEFAULT 'user'
    CHECK (role IN ('user', 'admin'));
```

⏱️ **实测结果**（`sqlite3` 直接执行，两种场景均验证）：

| 场景 | 命令 | 结果 |
|---|---|---|
| 空库建表后 ALTER | `ALTER TABLE users ADD COLUMN role ... CHECK (...)` | ✅ 成功，`role` 默认 `'user'` |
| **已有数据的真实库**（本项目 `schema.sql` + `seed.sql`，含 `id=0` 哨兵） | 同上 | ✅ 成功，哨兵自动获得 `role='user'` |
| 写入合法值 `'admin'` | `INSERT ... role='admin'` | ✅ 接受 |
| 写入非法值 `'bogus'` | `INSERT ... role='bogus'` | ✅ **被拒绝**：`CHECK constraint failed: role IN ('user','admin')` |

> 📌 **两条关键结论**：① SQLite 的 `ADD COLUMN` **允许**带 `CHECK` 约束（已验证），因此不需要重建表；② 游客哨兵（`id=0`）自动落到 `role='user'`，**不会**因为默认值而意外获得管理员权限。

**是否加索引**：❌ **不加**。理由：`role` 只有 2 个取值，基数极低，索引选择性差；且管理端「用户列表」是全量分页（不是按 role 高频筛选），加索引的收益低于维护成本。

#### 5.3.2 变更二：`operation_logs.action` CHECK 由 7 类扩为 8 类

**问题**：现有 `action` 的 CHECK 为 7 类 `('login','register','logout','upload','predict','export','delete')`。管理端四类新动作——**停用/启用用户、重置密码、切换模型版本、强制删除任务**——中只有「强制删除」能勉强映射到 `delete`，其余无对应值。若不处理，管理端操作**无法写入审计日志**，`AD-P02` 的操作日志页会出现审计盲区。

**方案（`QD-02`，建议采纳 A）**：

| 方案 | 做法 | 值数 | 评价 |
|---|---|---|---|
| **A（建议）** | 增 1 个值 `'admin'`，管理端子动作写入 `detail`（结构化文本，如 `sub=user_disable;target_user=3;by=1`） | **8** | CHECK 保持紧凑；管理端操作量小，筛选用 `detail` 前缀即可 |
| B | 拆成 4 个独立值 `admin_user_update` / `admin_user_reset_pwd` / `admin_task_delete` / `admin_model_activate` | 11 | 可筛选性最好，但值集开始膨胀，接近枚举反模式 |

**建议方案 A 的 DDL**：

```sql
    action      TEXT    NOT NULL                            -- 8 类操作（FR-SYS-03 四类核心动作的超集 + 管理端子层 CH-01）
                CHECK (action IN ('login', 'register', 'logout', 'upload', 'predict', 'export', 'delete', 'admin')),
```

⏱️ **实测约束**：SQLite **不支持修改已有列的 CHECK**，必须走表重建：

| 场景 | 处理方式 |
|---|---|
| **A：库中尚无生产数据（本期适用）** | 直接修改 `schema.sql` 建表语句 → 重建库。**零风险**，无需 12 步流程 |
| B：库中已有数据 | 按 SQLite 官方 12 步「表重建」流程（建新表 → `INSERT INTO ... SELECT` 拷数据 → `DROP` 旧表 → `RENAME` → 重建索引）。`operation_logs` 无外键指向它，重建成本可控 |

> 📌 本期属场景 A（`data/app.db` 尚未产生，`operation_logs` 无数据），因此**只需改 `schema.sql`，不需要写复杂的迁移脚本**。迁移脚本仍按 §5.3.4 统一登记，以备后续环境。

#### 5.3.3 变更三：`seed.sql` 内置管理员种子账号

```sql
-- CH-01：管理员种子账号（幂等，可重复执行）
-- ⚠️ 邮箱域名必须能被 Pydantic EmailStr 接受，否则 LoginRequest 会先拒掉登录请求（见下方实测）
INSERT OR IGNORE INTO users (email, password_hash, nickname, status, role)
VALUES ('admin@salesforecast.cn', '<bcrypt 串，由 scripts/ 一次性生成>', '系统管理员', 1, 'admin');
```

> 🔒 **实测确认的陷阱（务必遵守）**：`LoginRequest.email` 的类型是 **`EmailStr`**（`code/backend/schemas.py:176`），而 `EmailStr` 会**主动拒绝 RFC 2606 保留域**。若种子管理员邮箱沿用游客哨兵的 `.invalid` 风格，管理员将**永远无法登录**——请求在 Pydantic 校验层就被拒掉，连密码比对都走不到。⚠️ 行号锚点会随 `schemas.py` 增删而漂移（`EP-4` 加过 16 行、`EP-5` 又加了 `HorizonEstimate` / `estimate_by_horizon` / `timing` 三处），**引用前先 grep 一次真实行号**。

| 候选邮箱 | `EmailStr` 判定 | 可否作管理员 |
|---|---|---|
| `admin@local.invalid` | ❌ `The part after the @-sign is a special-use or reserved name` | ❌ |
| `admin@salesforecast.local` | ❌ 同上（`.local` 同属保留域） | ❌ |
| **`admin@salesforecast.cn`** | ✅ 接受 | ✅ **推荐** |
| `admin@example.com` / `admin@test.com` / `admin@forecast.internal` | ✅ 接受 | ✅ 可用 |

> 📌 **与游客哨兵的对照**：游客哨兵用 `.invalid` 域是**刻意的安全设计**——它使哨兵账号天然无法登录（无需额外代码防护）。管理员种子账号的目标相反（**必须能登录**），因此**两者的域名策略必然不同**，不可互相复制。

> ⚠️ **密码强度须与注册规则一致**（`FR-USR-02`）：≥ 8 位、同时含字母与数字、**≤ 72 字节**（`JT-12`）。生成 bcrypt 串时须使用与运行时一致的 `bcrypt==5.0.0` 与 cost 因子，否则校验失败。

### 5.4 数据隔离红线的例外设计（🔒 安全核心）

#### 5.4.1 红线原文与例外的边界

PRD §3.2 规定：**「任何接口的查询条件必须携带当前用户 ID 作为过滤条件，这是数据隔离红线（`NFR-SEC-02`）。」**

管理端需要跨用户读取数据——这是该红线的**第一个、也是唯一的显式例外**。例外必须被**精确圈定**，不能扩散：

| 维度 | 普通用户接口（21 个） | 管理端接口（新增 9 个） |
|---|---|---|
| 数据范围 | 仅 `user_id = 当前用户` | 全量 |
| 鉴权依赖 | `get_current_user` | **`get_current_admin`**（在 `get_current_user` 基础上强制 `role == 'admin'`） |
| 未授权响应 | `401`（未登录） | `403`（已登录但非管理员） |
| 审计 | 部分操作记 `operation_logs` | **每个写操作必须记**（`action='admin'`） |
| 出现位置 | `app/api/v1/*.py`（5 个文件） | **仅 `app/api/v1/admin.py` 一个文件** |

> 🔒 **`BE-ADM-01`：例外只允许存在于 `admin.py`。** 任何在 `auth.py` / `datasets.py` / `predictions.py` / `history.py` / `system.py` 中出现「不带 `user_id` 过滤的查询」都视为**红线破坏**，代码评审直接打回。建议用 `ruff` 自定义规则或评审检查单（技术文档 `REV-1`）强制。

#### 5.4.2 三条必须同时满足的安全约束

| # | 约束 | 落地要求 |
|---|---|---|
| 1 | **强制角色校验** | `get_current_admin` 必须在**每一个**管理端接口上声明；禁止在路由函数内部「先查后判」（漏判即越权） |
| 2 | **全操作审计** | 管理端 4 类写操作（启停用、重置密码、强制删除、切换模型）全部写 `operation_logs`，`action='admin'`，`detail` 记子动作 + 操作者 + 目标 |
| 3 | **最小暴露** | 管理端**不返回**用户密码哈希、不提供原始 CSV 内容下载（`QD-04`）；手机号/邮箱等个人数据按 `NFR-SEC-05` 脱敏规则处理 |

#### 5.4.3 越权判定的顺序（沿用 `BE-41`，不得简化）

```
请求进入
  ├─ 携带 Token？
  │   ├─ 否 → 401（未登录）
  │   └─ 是 → 校验签名 + 到期时间 + token_version
  │       ├─ 失败 → 401（Token 失效）
  │       └─ 成功 → 取 user_id
  │           ├─ role != 'admin' → 403（E_FORBIDDEN）
  │           └─ role == 'admin' → 通过，进入业务
  └─ 管理端特有：写操作 → 先落审计日志，再执行
```

> 📌 **注意 `token_version` 的联动**（数据库设计文档 §10.5）：管理员**重置用户密码**时，必须同时把该用户 `token_version + 1`，使该用户所有旧 Token 立即失效——否则「重置了密码但攻击者手上的 Token 还能用」，重置形同虚设。

#### 5.5.1 `API-29` 的事务顺序（🔒 必须严格照此实现）

`model_registry` 上有**部分唯一索引** `ux_model_active ON model_registry (is_active) WHERE is_active = 1`，保证「全局有且仅有一个启用版本」。

⏱️ **实测验证**：

| 操作 | 结果 |
|---|---|
| `BEGIN; UPDATE ... SET is_active=0 WHERE is_active=1; UPDATE ... SET is_active=1 WHERE version='lstm_v2'; COMMIT;` | ✅ 正确切换（`lstm_v1=0`, `lstm_v2=1`） |
| 跳过第一步，直接把 `lstm_v1` 也置 1 | ✅ **被拒绝**：`UNIQUE constraint failed: model_registry.is_active` |

> 🔒 **`BE-ADM-02`：两个 `UPDATE` 必须在同一事务内，且顺序固定（先降旧、再升新）。** 顺序颠倒或分两次提交都会撞唯一索引失败。
>
> 🔒 **`BE-ADM-03`：切换版本后必须校验与 `.env` 的 `ACTIVE_MODEL` 一致**（技术文档 `BE-06`）——不一致会导致「数据库说启用了 v2、进程实际加载 v1」的静默故障。实现方式：切换接口在事务提交后触发模型重载，或返回提示要求运维同步 `.env` 并重启。

#### 5.5.2 `API-27` 强制删除的级联范围

| 表 | 处理 | 依据 |
|---|---|---|
| `tasks` | 删除 | 目标对象 |
| `predictions` | 级联删除 | 外键 `ON DELETE CASCADE`（`FK-*`） |
| `metrics` | 级联删除 | 同上 |

## 6. 实施阶段划分

### 6.1 阶段划分原则

| # | 原则 | 说明 |
|---|---|---|
| 1 | **每阶段以「可运行、可演示」收口** | 不允许出现「半成品阶段」（开发方案 §7.1） |
| 2 | **算法链路优先于界面美化** | 先用脚本跑通算法，再接 Web。否则联调期会同时面对算法与接口两类问题 |
| 3 | **不可逆依赖前置** | 数据库、认证先于业务；业务先于聚合视图（管理端放在业务之后） |
| 4 | **风险最高的阶段给足余量** | `EP-5` / `EP-6`（预测链路 + 结果页）是唯一有硬指标门槛的阶段 |
| 5 | **每阶段结束做一次演示** | 未通过不进下一阶段（`DOD` 逐条核对） |
| 6 | **单人开发 → 严格串行** | 阶段之间不并行；同阶段内可并行前后端，但以「后端接口自测通过 → 再写前端」为准（避免同时面对两端问题） |

> | **现象** | `horizon=30` 实测 **72.2 s**，`status=failed`（软失败），**击穿 60 s 硬约束**。而同一份数据 `h=7` 仅 17.5 s、`h=14` 31.3 s —— 耗时随步长**超线性**增长 |
> | **根因** | `algo.infer._roll_multistep` 每一步都调用 `features.build_inference_windows`，而后者的实现是「先对**整条序列**建 pandas 特征表（`to_datetime` + `strftime` + `isin` + `shift` + 2 × `rolling` + `concat`）、**再取最后 `window` 行**」⇒ 同一条序列被**重复建表 `horizon` 次**，且每次都付全额 pandas 固定开销 |
> | **为什么 60 s 是**「勉强够」**而非余量充足** | 一次批量前向仅 **95 ~ 163 ms**（毫秒级，`DOD` 第 2 条正是这么要求的）。也就是说**性能全在滚动多步的 Python 侧循环里**，不在模型里 |
> | **先排除的方案** | `scripts/_ep5_bench_roll.py` 先试「只取尾部切片」—— 实测仅省 **11%**。因为瓶颈是 pandas 每次调用的**固定开销**（函数入口、列名构造、对象创建），不是行数 |
> | **最终修复** | 新增 `features.calendar_matrix(dates)` 一次算好 `(n, 6)` 日历矩阵 + `features.last_window_fast(cal, sales)` 用纯 numpy 取尾窗。**等价性而非近似**：窗口内各列只依赖向前的至多 `ROLL_WARMUP=14` 个值（`lag_1`→1、`lag_7`→7、`roll_mean_7=shift(1)+rolling(7)`→8、`roll_mean_14`→15），其余 6 列（`sales`/`dow_sin`/`dow_cos`/`month_sin`/`month_cos`/`is_weekend`/`is_holiday`）逐行独立 |
> | **踩坑点** | `_trailing_mean` **必须用 `sliding_window_view`**（O(m·w)，w 只有 7/14），不能用 `cumsum` 差分 —— 后者引入累加误差，会破坏与 pandas 的**逐位相等** |
> | **修复后** | h=7 **11.3 s** / h=14 **16.6 s** / h=30 **23.8 s**（重复测量稳定），三档均留有 2.5 倍以上余量 |
> | **等价性证明** | `scripts/verify_ep5_equiv.py` 把改造前的 `_roll_multistep` **逐字保留**为 `reference_roll`，对全部 **81 条 L1 序列 × 3 档步长**断言 `np.array_equal` → **3/3 通过**。同时重跑 `eval_report.py --demo --horizon 14`，指标**逐位不变**（14.26 / 26.42 / 27.52 / 83.95，覆盖 L1 81 / L2 32 / L3 0 / 合计 113） |
> | **回归守卫** | `verify_ep5.py` 附加项：用 AST **只查 `_roll_multistep` 函数体内**的可执行代码，断言不含 `build_inference_windows` 调用。⚠️ 不能全文匹配 —— `run_inference` 里第 163 行仍合法调用它（那是**一次**批量前向，建一次表是对的），且文件注释里多处提及该函数名 |

> > ### 7.7.3 `EP-6` 校验脚本自身的 5 处判据错误（**代码是对的，判据写错了**）

> > ③ **`register` 响应不返 Token**：`RegisterResponse` 契约只有 `user_id` / `email`，早期版本直接取 `data.access_token` 恒为 `None`，后续所有带鉴权的用例全降级成游客。

> ### 7.8.2 `EP-7` 修复的 5 个真实缺陷
>
> **① 🔴 `soft_delete` 用 `{Task.is_deleted: 1}` 作字典键（潜伏缺陷）**
>
> `task_dao.soft_delete` 写的是 `where(Task.id == task_id).values({Task.is_deleted: 1})`，而字典键必须是**字符串列名**；SQLAlchemy 2.0 会抛 `InstrumentedAttribute is not supported`。这是**潜伏缺陷** —— 函数从 `EP-1` 起就存在但从未被调用过，`API-20` 是第一次触发。改为 `{"is_deleted": 1}`。
> 📌 **教训**：DAO 层写完不等于被调用过。删除类函数天然是"最后才跑一次"，所以最容易藏着笔误。
>
> **② 🔴 `v_task_summary` 视图缺 `dataset_id`，原参数重试要多查一次**
>
> 视图原先只外露 `dataset_name`（展示用字符串）。但 `API-19-1` 的「原参数重试」需要 `dataset_id` + `horizon`，前端想跳重试就**得再查一次详情**才能拿到 id —— 多一次往返，且详情可能已不可用。`dataset_id` 是外键不是业务数据，外露无隔离风险。三处同步修（`schema.sql` / 实际库 `DROP VIEW`+`CREATE VIEW` / 数据库设计文档新增设计要点）。
>
> **③ 🔴 软删除后详情仍可访问（列表与详情口径不一致）**
>
> `result_service._owned_task` 用 `get_by_id` 查，**不过滤 `is_deleted`** —— 于是任务从列表消失了，但直接输 `/history/{id}` 还能打开（`predictions` 还在）。用户视角就是"删了但没删掉"，且列表说没有、详情说有，**同一任务两处口径矛盾**。修法：`_owned_task` 一律把软删除视为不存在（返 `40401`）；`soft_delete` 的幂等实现改为**不走 `_owned_task`**，先 `get_by_id` 校验归属、再判`is_deleted == 1` 直接返成功。
> 📌 **推论**：凡"列表里过滤 + 详情里不过滤"的字段，两个地方必须同步。已固化进 `verify_ep7.py`。
>
> **④ 🔴 失败任务历史详情整页 500**
>
> 失败任务可能连 `metrics` 行都没有（分级阶段就挂了）。此时 `timing_ms` 返回 `{}`，pydantic 因 5 个必填字段缺失抛 `ValidationError` → **历史详情页整页 500**。改为返回满零值（`total_ms` 取 `task.duration_ms`）。
>
> **⑤ 🔴 `TaskBrief` 静默丢弃失败三字段**
>
> 服务层返回了 `error_code` / `error_msg` / `completed_stage`，但 `code/backend/schemas.py` 的 `TaskBrief` 没声明这三个字段 —— **pydantic 会把未声明字段直接丢掉**，响应里根本没有，前端拿到 `undefined`，看起来像"后端没存失败原因"。补声明三字段（成功任务为 `null`）。
> 📌 **通用教训**：pydantic 不会报错、只会**静默丢字段**。服务层加了返回字段却"前端拿不到"，第一反应就查 schema。

> > **① 失败任务在「结果页」与「历史详情页」表现相反，是刻意的。**
> > `EP-6` 定的规则是：失败任务进结果页 → 返 `40401`，**不给半成品**。`EP-7` 反过来：历史详情页**必须**展示 `error_code` / `error_msg` / `completed_stage` + 归因 + 原参数重试入口。
> > 理由：这两个页面对应**两个不同的用户诉求**。「预测是否成功」由结果页回答（用户刚发起，最关心这个）；「上次为什么失败、怎么改参数重试」由历史详情页回答（用户回看，需要可行动信息）。若历史页也返 404，用户会发现失败任务**彻底无法查看原因**，只能重跑一次碰运气。
> >
> > **② `UX-P11` 最优值高亮必须逐行独立判断方向。**
> > `MAPE` / `MAE` / `RMSE` / 耗时是**误差与耗时类，越小越好取 `min`**；提升率与达标占比是**越大越好取 `max`**。写死一种方向会让一半的行高亮成最差值 —— 看起来"这任务最好"，实际最差。已实现 `lowerIsBetter ? Math.min(...) : Math.max(...)` 逐行求最优，且跳过 `null`（无法评估不参与比较）。
>
> **`EP-7` 的 5 个真实缺陷与 6 处判据错误**（详见 §7.8.2 / §7.8.3）：最值得记的是**缺陷③与①的组合** —— `soft_delete` 里藏着一个从未被调用过的笔误（①），而"列表过滤、详情不过滤"（③）又让它有机会被提前发现。**潜伏缺陷与口径不一致往往成对出现**：一个没被调用的函数，恰好是另一个口径漏洞的检测点。另一条是缺陷⑤：**pydantic 静默丢字段**不报错、不告警，服务层加了字段前端却拿不到，这类"看起来像后端没存"的现象，第一反应要查 schema 声明。

> ### 7.9.2 `EP-8` 修复的 3 个真实缺陷
>
> **① 🔴 停用用户仍能重新登录（安全缺陷，本阶段最严重的一个）**
>
> `auth_service.login()` 从 `EP-2` 起就**只校验密码，完全不看 `user.status`**。于是 `API-24` 把用户停用（`status=0`）后，他只要重新登录一次就能拿到新 Token —— **停用形同虚设**，且这条路径完全绕开了管理端的全部审计。
>
> 修法：在密码校验成功之后、签发 Token 之前补状态检查，失败时写一条 `result='fail'` 的登录日志并返 `BAD_CREDENTIAL`（🔴 **不返「账号已停用」** —— 那等于一个可枚举的账号状态探测接口）。
> 📌 **教训**：**"封禁"类需求必须同时堵三条路**：已有 Token（靠 `token_version`）、重新登录（靠 `status` 检查）、API 直调（靠 `get_current_admin`）。`EP-8` 三条都补齐了，但**只有第2 条是这次才发现的** —— 前两条在 `EP-2` 就写了，第 3 条在 `EP-8` 才写。封禁功能天然是"三处协同"，漏一处不会报错、只会漏防。
>
> **② 🔴 `NoticeBar` 静默丢弃 `data-testid`**
>
> `NoticeBar` 的 `Props` 是封闭对象类型，**不透传任意 DOM 属性**。`AdminManagePage` 在删除成功回执上写了 `data-testid="ok-msg"`，TypeScript 因为索引签名缺失而没有报错（调用方多传属性在有默认导出的组件上容易漏检），运行时 React 直接把这个属性**丢掉** —— 页面显示完全正常，但验收脚本永远断言不到，且**不产生任何错误信息**。
>
> 修法：`Props` 加 ``[key: `data-${string}`]: unknown`` 并 `...rest` 透传。
> 📌 **教训**：**"页面正常但断言断言不到"是比"页面报错"更难查的一类失败**，因为没有任何错误线索。本次靠"删除后弹窗关闭 ✅ 但回执 ❌"这个不对称组合才定位到 —— 若当时把两项一起断言失败，就会误判成"删除功能整体没做"。
>
> **③ 🔴 ECharts 主包体积回归（`EP-3` 成果被推翻）**
>
> `EP-3` 曾把主包从 1381 kB 降到 343 kB（ECharts 拆成独立分包 + 懒加载）。`EP-8` 首次构建时主包又涨到约 **1.57 MB**。根因不是 `EP-8` 自己引入了 ECharts，而是**`EP-6` 的 `LineCompare` / `DistributionChart` 在模块顶层静态 `import EChart`**，把整条静态引用链拉回主包。
>
> 修法：两处改 `lazy(() => import('../EChart'))` + `Suspense`（fallback 用既有 `Skeleton`）。修复后主包 **534 kB**，ECharts 独立为约 **1015 kB** 分包。
> 📌 **教训**：**懒加载的收益会被"后来者在别处静态 import 同一模块"悄悄抹掉**。这类回归不会报任何错，只是构建产物变大，必须靠"每阶段都记基线数字 + 每阶段都比"这套纪律才能发现。同理，剩余 534 kB 主要来自 antd / react-dom，是 `EP-4` 之后的合理增长，**不是 echarts 回归** —— 别看到"超过 EP-3 的 343 kB"就再去拆包。

> ### 7.9.4 `EP-8` 排查最耗时的一个根因：代理端口不匹配
>
> 浏览器走查初次运行只有 **27/60**，且失败极具迷惑性：普通用户"登录失败"、管理员登录成功但页面**数据全空**、所有表格 0 行、弹窗不出现。
>
> 真实原因有**两层**，都不在业务代码里：
>
> 1. **旧进程占端口**：5199 / 8021 上还挂着 `EP-8` 之前启动的进程，本次启动的新后端因`Errno 10048` 直接退出。运行中的旧后端 `openapi.json` 里**一条 `/admin/*` 路由都没有**（实测只有 21 条），前端自然什么都拿不到。
> 2. **vite 代理目标不匹配**：`vite.config.ts` 的 `VITE_API_TARGET` 缺省是 **8000**（技术文档 §2.7 的约定端口），而测试后端跑在 **8021**。前端日志里是 `http proxy error: /api/v1/auth/login Error: connect ECONNREFUSED 127.0.0.1:8000` —— **后端日志里一条请求都没有**。
>
> 第 2 点是真正的元凶，且它**伪装成业务 bug**：页面能渲染、无空白、控制台也不报错（`consoleErrors=0`），只是数据永远为空。
>
> 📌 **教训（已固化进 `vite.config.ts` 文件头）**：启动 dev server **必须**带 `VITE_API_TARGET=http://127.0.0.1:<后端端口>`。判断代理是否通，看**后端**日志有没有请求最直接 —— 后端零请求 = 请求根本没到后端 = 代理配错，不要再去查前端代码。
>
> 另外还发现一处**脚本自身的脆弱点**：注册表单底部有《用户协议》《数据用途说明》两个必选复选框，脚本从未勾选，被前端校验拦下并停在 `/register`，表现为"登录失败"。已在脚本里显式勾选并新增一条断言（`注册页用户协议已勾选`）。同时把普通用户邮箱改为**时间戳**（`ep8b_${Date.now().toString(36)}@verify.com`）—— 邮箱全局唯一，固定邮箱导致脚本**第二次跑就必然失败**，验收脚本必须可重复执行。

**十八条最易踩的坑（本项目已验证）**、

| # | 坑 | 后果 | 防法 |
|---|---|---|---|
| 1 | 用户侧「错误明细」与正式导出未分目录 | 临时文件被 7 天清理误保留 | 分目录 `exports/tmp/`，TTL 1 小时 |
| 2 | `POST /history/compare` 注册在 `/history/{task_id}` 之后 | `compare` 被当 task_id，报 `40012` | 路由注册顺序固定 |
| 3 | 管理端种子邮箱用 `.invalid` 域 | 管理员永远无法登录（`EmailStr` 先拒） | 用 `admin@salesforecast.cn` |
| 4 | **`services/` 里做完状态变更后 `raise BizError`，指望 `get_db` 提交** | `get_db` 契约是「异常→rollback」，**变更被回滚**。`EP-2` 的实测后果是**登录限流永不生效**（fail_count 每次归零）；`EP-4` 的实测后果是**五类校验失败一条记录都不落库**，`API-11` 的错误明细永远拿不到；`EP-5` 的实测后果是**超时软失败任务查不到** | 需要保留的副作用**在抛错前显式 `db.commit()`**（`BE-17` 的正当例外）。判据：这条缺陷**在单次请求的返回值上看不出来** —— 接口该报的错都报对了，只有再查一次库才露馅（`EP-4` 的原话是「复现得了但查不到」） |
| 5 | 用 `datetime.min` / `0` 之类的「哨兵时间」表示「未锁定」 | 「判断是否已解锁」的 `remain <= 0` 会同时命中「根本没锁」→ 误删正在累积的计数 → **限流静默失效**（`EP-2` 实测） | 「计数中」与「已锁定」必须用**不同的类型**表达（如 `None` vs `datetime`） |
| 6 | **图表依赖 ECharts「默认色板按系列序号取色」** | 只要有「不可见/占位」系列（如置信带），线条拿到的颜色就会后移，**自绘图例与图表颜色对不上**（`EP-3` 实测：线条是橙/红，图例画的是青/绿） | 需要与图例严格一致时，系列**显式绑定令牌色**（`readTokenVar('--c1')`），并让 option 以主题为依赖重建 |
| 7 | **主题相关逻辑写在 store 里、且 store 静态 `import` 了重型图表库** | ① 图表库被打进主包，懒加载形同虚设（`EP-3` 实测主包被 ECharts 撑到 1.38 MB）；② 注册发生在 CSS 注入之前 → `getComputedStyle` 取到**空色板** | 让**唯一使用者**在 `init()` 前同步注册（图表组件内），store 只维护 `isDark` 状态；主包随即从 1381 kB 降到 343 kB |
| 8 | **拿正则扫源码做「痕迹/字面量」守卫，却不先剥注释** | 注释里写「已移除 `X`」反而被判违规 —— 守卫变成噪音，最后被人关掉（`EP-1` 已踩过一次，`EP-3` 又踩，`EP-5` 第三次） | 守卫一律先剥 `//` 与 `/* */` 再扫；能用 AST 就别用正则（`EP-4` 已改用 `ast.walk` 取真实 import） |
| 9 | **无头浏览器复用固定 `--user-data-dir`，且只 `edge.kill()` 父进程** | 上次残留的子进程仍持有 profile 锁 → 新实例**静默挂起**：不报错、不产出一张截图、脚本空转 15 分钟（`EP-4` 实测）。任何「一直不结束也不报错」的自动化都先怀疑资源锁 | ① 每次用全新 profile 目录；② 退出时 `taskkill /PID <pid> /T /F` 杀**进程树**；③ 调试端口按 PID 分散并在起跑前自检未被占用；④ 给单次截图套 15 秒上限（`captureScreenshot` 的 CDP 超时是 120 秒，先挂两次就是 4 分钟） |
| 10 | **用同一族选择器取值（`[data-testid=x] span`）或按下标取兄弟节点（`aside[1]`）** | 把不该收的节点一起收进来：徽标的 `span` 把内部 ✓/✗ 图标也收了（长度翻倍）；模板 B 的 `aside[0]` 是导航侧栏、右栏其实在 `[1]` —— 断言会稳定地取到错误对象（`EP-4` 实测两类各一次，`EP-5` 又在 `data-testid` 落点与选择器层级上踩了 4 次） | 选择器限定到**承载语义的那一层**；兄弟节点**按内容查找**而不是按下标。⚠️ 更根本的防法是**先给组件加稳定的 `data-testid`**，而不是让走查脚本去猜 DOM 结构 |
| 11 | 🔴 **滚动多步推理里，每步都调「整条序列特征表」构建器** | 同一条序列被重复建表 `horizon` 次，`horizon=30` 实测 **72.2 s** —— **击穿 60 s 硬约束**（`EP-5` 实测）。且耗时随步长**超线性**增长（h=7 17.5 s → h=30 63.9 s 软失败） | 把「取尾窗」从 pandas 路径里拆出来：用纯 numpy 一次算好日历矩阵 + 向量化取窗（`features.calendar_matrix` / `last_window_fast`），降到 **23.8 s**。⚠️ 两条配套：① `_trailing_mean` **必须用 `sliding_window_view`**，用 `cumsum` 差分会引入累加误差、破坏与 pandas 的逐位相等；② 先试「只取尾部切片」只省 11% —— 瓶颈是 pandas 每次调用的**固定开销**，不是行数 |
| 12 | 🔴 **同一族概念存在两个「耗时」口径却共用一个字段** | 「单遍评测 7,873 ms」与「任务端到端 16,618 ms」差一倍以上，共用一个字段会让参数页显示「预估 7.9 s、实际 16.6 s」；更糟的是**校验脚本拿 7,873 去比端到端预估，得出「偏差 99%」的假告警** | 并列两个字段并各自命名语义：单遍 `estimated_ms`（评测基准）+ `estimate_by_horizon[]`（端到端预估）。**每个耗时字段都要在文档里写明它是哪一遍**（`EP-5` 登记为口径偏离 ③） |
| 13 | 🔴 **同进程改 `Settings` 属性来构造「换个配置」的用例** | `@dataclass(frozen=True)` ⇒ 直接 `FrozenInstanceError`；若改成非 frozen 又会污染后续用例 | 「换个配置再跑一次」只能**独立子进程 + 环境变量**（`EP-5` 的 `scripts/_ep5_cfg_probe.py`）。同理，**模块级单例**（如模型 holder）也不能同进程换设备 —— CPU/GPU 一致性验证必须两个进程各跑一份，否则比对到的是缓存句柄的「假一致」 |
| 14 | 🔴 **按 RESTful 直觉断言业务错误的状态码** | 本项目契约是 **HTTP 200 + `body.code`**（除 401 类，见 `errors.py::register_exception_handlers`），判据写 `status == 400` 会**全部假失败**，而真正要拦的红线（软失败不得退化成 5xx）反而没被测到 | 断言 `body.code`；并单独加一条「业务错误**不是** 4xx/5xx」的守卫，防止有人把契约改成 RESTful（`EP-5` 踩过，8 处判据错误里最易复发的一条）。**口径注（2026-10-26，`R-09`）**：「不得退化成 5xx」这条红线现在收窄为「**软失败路径**不得返 5xx」—— `code >= 50000` 的服务端故障已改为返回真实 HTTP 500，故守卫须按 `body.code` 区间判定，不能笼统断言 `status != 5xx` |
| 15 | 🔴 **依赖注入写成 `user=CurrentUser`（默认值形式）而非 `user: CurrentUser`（注解形式）** | 传进去的是**类本身**不是实例，`user.id` 拿到的是 SQLAlchemy 的 `InstrumentedAttribute` —— 不报错，一路带到 DAO 层才炸，且报错信息完全指不到真正的原因 | `Annotated[X, Depends(...)]` 只能走**注解形式**。判据：FastAPI 依赖用默认值写法，本质上就是「给形参声明了一个默认值」，语法合法、类型检查也过得去（`EP-7` 踩过，4 处） |
| 16 | 🔴 **服务层加了返回字段，但 schema 没声明** | **pydantic 静默丢弃**未声明字段：不报错、不告警，响应里就是没有。前端拿到 `undefined`，看起来像「后端没存失败原因」，排查方向会整个跑偏 | 服务层返回结构与 schema **逐字段对齐**；schema 变更后跑 `verify_schemas.py`。判据：任何「后端明明返回了、前端就是拿不到」的现象，第一反应查 schema 声明（`EP-7` 实测：`TaskBrief` 丢 `error_code`/`error_msg`/`completed_stage`） |
| 17 | 🔴 **「列表里过滤 + 详情里不过滤」用了不同口径** | 软删除的任务从列表消失了，直接输 `/history/{id}` 却还能打开（`predictions` 还在库里）。用户视角是「删了但没删掉」，且同一任务两处口径矛盾 | 凡「列表过滤、详情不过滤」的字段，两处**必须同步**判定。修法要点：**判不存在**与**判幂等**要拆开 —— `_owned_task` 一律把软删除视为不存在（返 `40401`），而软删除的幂等分支改走 `get_by_id` 自判，不复用它（`EP-7` 实测，见 §7.8.2 ③） |
| 18 | 🔴 **DAO 层的删除类函数从写完起就没人调用过** | `soft_delete` 用 `{Task.is_deleted: 1}` 作字典键（须为字符串列名），SQLAlchemy 2.0 抛 `InstrumentedAttribute is not supported`。潜伏到 `API-20` 第一次真正调用才暴露 | DAO 写完≠被调用过。**删除类函数天然「最后才跑一次」**，最容易藏笔误 —— 且它往往同时是另一处口径漏洞（#17）的检测点。判据：新增写操作 DAO 时，手工构造一次调用断言，不要指望集成阶段才发现 |
