## 1. 背景与目标

### 1.1 项目背景

中小电商商家的补货决策长期依赖经验判断：运营人员凭"上次卖得不错""感觉要涨价"来决定采购量，缺乏量化依据，导致两类损失同时存在——**备货不足**（断货、错失销售窗口）与**备货过剩**（占压资金、产生滞销与仓储成本）。专业销量预测工具要么是大型 ERP 的昂贵模块，要么需要数据分析能力，中小商家两者都不具备。

商家手中实际已有可用的数据资产：电商后台可导出历史销量明细（含商品、分仓、日期、销量），格式为 CSV。缺的只是一个"上传即出结果"的工具。

### 1.2 产品目标

| 层级 | 目标 | 衡量方式 |
|---|---|---|
| 产品目标 | 让不懂算法的运营人员在 5 步操作内拿到未来 7/14/30 天的分仓销量预测 | 主干路径操作步数 ≤ 5，端到端 ≤ 1 分钟 |
| 算法目标 | 预测精度显著优于朴素方法，且达到可交付水准 | 加权 MAPE ≤ 20%；加权 MAE/RMSE 相对移动平均基线降低 ≥ 15% |
| 工程目标 | 在 2GB 显存的普通笔记本上稳定提供预测服务 | 全量数据推理端到端 ≤ 1 分钟；GPU 不可用时自动回退 CPU 且结果一致 |
| 交付目标 | 完成课程/答辩要求的全套交付物 | 任务书 5.1 / 5.2 清单 100% 齐备 |

### 1.3 项目范围（In Scope）

- 用户注册 / 登录 / 登出
- 历史销量 CSV 上传、字段校验、数据预览、标准模板下载
- 内置示例数据一键加载（菜鸟数据集抽样）
- 数据清洗（缺失插值、异常截断）、特征工程、序列分级
- 基于预训练 LSTM 的多步销量预测（7 / 14 / 30 天）
- 移动平均基线的同期对照计算
- 预测结果可视化（曲线、指标卡、分商品表格、覆盖率披露）
- 结果导出（CSV / Excel）
- 历史记录列表、详情、跨任务对比、删除
- 系统级能力：统一错误结构、日志、健康检查、免责声明、HTTPS

### 1.4 明确不在本期范围（Out of Scope）

| 不做的事 | 理由 |
|---|---|
| ❌ 实时 / 流式销量接入（对接 ERP、电商后台 API） | 本期只做 CSV 文件上传 |
| ❌ 自动补货下单、库存联动、一键采购 | 属决策执行类功能，超出预测工具边界 |
| ❌ 多租户 SaaS、组织架构、**多角色 RBAC**（角色间可配置权限矩阵） | 本期引入**单一管理员角色**（`user` / `admin` 两值，`CH-01`），不含多角色 RBAC |
| ❌ 移动端原生 App | 响应式 Web 已满足任务书要求 |
| ❌ 用户上传后即时训练模型 | 📌 受 1 分钟等待上限约束，训练无法在该时限内完成；系统统一使用预训练模型推理 |
| ❌ 模型在线增量训练、自动重训调度 | 属 V2.0 迭代项 |
| ❌ 第三方登录（微信 / 支付宝 / 短信验证码） | 本期仅邮箱密码注册 |
| ❌ 多语言界面 | 本期仅简体中文 |

> **范围红线**：以上条目在 MVP 阶段不得以任何形式进入开发排期。若确有需要，走变更流程并同步下调同等工作量的其他需求。

### 2.3 核心业务流程图（主干路径）

```
[1] 访问站点
     ├─ 未登录 ──→ 登录/注册页 ──→ [2]
     └─ 已登录 ──→ 工作台 ──→ [3]

[2] 注册 / 登录   → 校验 → 签发 Token → 前端存储

[3] 新建预测任务
     ├─ 方式 A：上传自己的 CSV
     └─ 方式 B：一键加载内置示例数据

[4] 数据校验（自动，秒级返回）
     必需字段（含仓库列）→ 日期可解析 → 时间连续性 → 销量非负 → 序列数上限
     ✗ 任一失败 → 结构化错误（错在哪 + 怎么改）→ 回 [3]

[5] 选择预测参数
     粒度：仓库 × 商品（固定）| 步长：7 / 14 / 30 天（默认 7）| 节假日特征：是/否（默认是）
     ❌ 无"是否重新训练"选项

[6] 后端执行预测流水线（同步执行，📌 目标 ≤ 1 分钟）
     清洗 → 按序列归一化 → 特征工程 → 序列分级 L1/L2/L3
       → L1 批量推理 / L2、L3 规则兜底 → 移动平均基线
       → 加权指标 + 达标序列占比 + 覆盖度统计
     ✗ 超时 → 软失败（明确提示，不返回 502）

[7] 结果展示
     曲线 + 指标卡 + 覆盖率披露 + 分商品表格（含粒度和置信度）
     ✗ 加权 MAPE > 20% → 页面显著位置提示"误差偏高，谨慎参考"

[8] 结果处置：导出 CSV/Excel | 自动存档到历史

[9] 历史记录：列表 → 详情 → 跨任务对比 → 再次导出 → 删除（二次确认）
```

## 3. 功能性需求

> 本章每个需求点均给出：编号、需求描述、优先级、验收要点。描述中**不使用"尽量""可能""大概"等模糊表述**，所有取值均为确定值或明确的待补充占位符。

### 3.1 `FR-USR` 用户管理模块

| 编号 | 需求描述 | 优先级 | 验收要点 |
|---|---|---|---|
| `FR-USR-01` | 用户使用**邮箱 + 密码**注册。邮箱全局唯一，重复注册返回明确提示 | P0 | 同邮箱二次注册被拒绝；邮箱格式校验在前后端同时执行 |
| `FR-USR-02` | 密码强度要求：长度 ≥ 8 位，且至少包含字母与数字两类字符。不满足时拒绝提交并说明原因 | P0 | 弱密码（如 `12345678`）被拒绝 |
| `FR-USR-03` | 密码**必须**以哈希形式存储（bcrypt 或等价算法），数据库中不得出现明文密码 | P0 | 直查数据库 users 表，密码字段为哈希串 |
| `FR-USR-04` | 用户使用邮箱 + 密码登录，成功后签发访问 Token（JWT）并返回用户基础信息 | P0 | 登录成功返回 Token；Token 含过期时间 |
| `FR-USR-05` | 用户可登出，登出后 Token 立即失效 | P0 | 登出后再用旧 Token 请求受保护接口，返回 401 |
| `FR-USR-06` | 连续 3 次密码错误后，该邮箱进入 60 秒冷却期，冷却期内登录请求被拒绝 | P1 | 第 4 次立即尝试被拒绝，提示剩余冷却时间 |
| `FR-USR-07` | 用户可查看与修改个人信息：昵称、密码 | P1 | 修改密码需输入原密码；修改后原 Token 失效并强制重新登录 |
| `FR-USR-08` | 未登录用户可**加载示例数据并看到完整预测结果**，但导出与历史记录功能需登录 | P1 | 游客态可跑到结果页；点击导出时弹出登录引导 |
| `FR-USR-09` | 找回密码（邮件重置链路） | P2 | MVP 阶段可用人工协助替代 |
| `FR-USR-10` | 第三方登录（微信 / 短信验证码） | P3 | 明确不在本期范围 |

> 📌 **角色模型**（`CH-01` 起修订）：本期引入**两种角色** —— `user`（注册用户）与 `admin`（管理员）。**不含多角色 RBAC**，管理员权限为**固定能力集**，不可配置。普通接口的查询条件**必须携带当前用户 ID 作为过滤条件**，这是数据隔离红线（见 `NFR-SEC-02`）。
>
> 🔒 **数据隔离红线的唯一显式例外**（`BE-ADM-01`）：管理端的 9 个接口（`API-22`~`API-30`）需要跨用户聚合运营数据，是本项目**唯一**不做 `user_id` 过滤的接口组。该例外被三重约束圈定：① 仅存在于 `app/api/v1/admin.py` 一个文件；② 每个路由必须声明 `get_current_admin`（已登录且 `role='admin'`，否则 `403`）；③ 4 类写操作全部写 `operation_logs`（`action='admin'`）。未登录请求仍为 `401`（**先认证后授权**，不可调换顺序）。

### 3.2 `FR-DAT` / `FR-UPL` 数据上传与校验模块

#### 3.2.1 上传与数据处理

| 编号 | 需求描述 | 优先级 | 验收要点 |
|---|---|---|---|
| `FR-UPL-01` | 支持**拖拽**与**点击选择**两种方式上传 CSV 文件，单文件，扩展名须为 `.csv` | P0 | 非 .csv 文件前端即时拦截 |
| `FR-UPL-02` | 提供"一键加载示例数据"入口，加载内置菜鸟数据集抽样文件 | P0 | 未上传任何文件的用户可据此跑通完整流程 |
| `FR-UPL-03` | 单文件大小上限 **20MB**，行数上限 **500,000 行**，超出即拒绝 | P0 | 21MB 文件被拒绝并提示上限值 |
| `FR-UPL-04` | 上传过程显示进度条；后端采用流式落盘，不一次性读入内存 | P1 | 20MB 文件上传过程中页面不卡死 |
| `FR-UPL-05` | 校验失败时返回**结构化错误**：错误类型 + 出错列名/行号 + 修复建议 | P0 | 前端能直接渲染出"缺少列：销量"这类可读提示 |
| `FR-UPL-06` | 提供"错误明细下载"，把不合格行导出为 CSV，便于用户在原表修正后重传 | P1 | 下载文件仅含不合格行且保留原始列 |

#### 3.4.3 指标口径定义（📌 确定值，不再讨论）

| 指标 | 公式 | 用途 |
|---|---|---|
| **加权 MAPE（主指标）** | `Σ\|yᵢ - ŷᵢ\| / Σ\|yᵢ\|`（即 WAPE） | 硬指标判定：**≤ 20%** |
| 加权 MAE | `Σ\|yᵢ - ŷᵢ\| / n` | 与基线对比：降低 **≥ 15%** |
| 加权 RMSE | `sqrt(Σ(yᵢ - ŷᵢ)² / n)` | 与基线对比：降低 **≥ 15%** |
| **达标序列占比** | 逐序列 MAPE ≤ 20% 的序列数 / 参与评估序列总数 | 辅助指标：**≥ 60%**（参考值，非硬卡点） |
| 基线 | **移动平均**，与主模型同预测点、同权重计算 | 对照基准 |

> **选择加权口径的理由**：长尾低销量序列的逐序列 MAPE 可达百分之几百，算术平均会使整体指标失去业务含义；加权口径对应"整体货量预测误差"，有明确业务解释，并天然规避零销量除零问题。

> 🔒 **硬指标判定组合**：加权 MAPE ≤ 20% **且** 加权 MAE/RMSE 相对移动平均基线降低 ≥ 15%。两项同时满足方判定达标。

| SQLite | 数据库 | 内置 | 中 | 见 `RK-06`；ORM 层不使用 SQLite 专有语法，保留迁移可能 | 后端 |
| 本地节假日表 | 节假日特征 | 随代码内置 | 低 | 内置含调休的节假日数据，运行时不联网 | 算法 |

### 6.3 内部依赖关系

```
数据集下载 → 算法链路（P1）→ 模型权重 → 后端服务（P2）→ 前端界面（P3）→ 集成联调（P4）
                ↓
         评估报告（硬指标证据）——须在 P1 结束前产出，否则 M-G1 里程碑不通过
```

> **关键路径**：`数据集 → 算法链路 → 模型权重` 是全项目关键路径。算法不达标则后续全部工序无法验证（后端能跑通但没有可用模型）。

## 附录 B：术语表

| 术语 | 含义 |
|---|---|
| SKU | 最小库存单位，即具体商品规格 |
| 序列（Series） | 一条 `sku_id + warehouse_id` 组合下的时间序列，本项目的最小建模单元 |
| MAPE | 平均绝对百分比误差，越低越好 |
| WAPE / 加权 MAPE | 按真实销量加权的 MAPE = `Σ\|y-ŷ\| / Σ\|y\|`，本项目**主判定口径** |
| MAE | 平均绝对误差 |
| RMSE | 均方根误差，对大误差更敏感 |
| 滑动窗口 | 用连续 N 天数据预测后续值，把时序样本化的方法 |
| 多步预测 | 一次预测未来多个时间点的值 |
| 移动平均基线 | 用近期均值外推的朴素方法，作为"模型是否真的有用"的对照，同时兼任长尾兜底模型 |
| 数据泄漏 | 训练时使用了未来信息，导致指标虚高、上线失效 |
| 早停 | 验证集误差不再下降时提前结束训练，防过拟合 |
| L1 / L2 / L3 | 序列三级分级：仓库×商品建模 / 降级到商品级分摊 / 标记不可预测 |
| 达标序列占比 | 逐序列 MAPE ≤ 20% 的序列数占参与评估序列总数的比例 |
| 预训练推理 | 加载离线训练好的模型直接推理，不在请求内训练 |
| granularity_level | 预测结果中标注该条记录所采用的分级层级（L1/L2/L3） |
