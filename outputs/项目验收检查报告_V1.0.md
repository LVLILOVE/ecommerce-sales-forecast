### `Y-06` 数据库备份能力 —— ✅ 已关闭（2026-10-21 10:14）

新增 `scripts/backup_db.py`。**不是**"调一下 `cp`"那么简单的封装，它解决的是三个真实坑：

| 坑 | 后果 | 脚本怎么处理 |
|---|---|---|
| WAL 模式下直接 `cp app.db` | 拿到**缺最新事务**的快照，看起来完整、实际丢数据 | 用官方 `sqlite3.Connection.backup()` 在线复制，**无需停服务** |
| 备份库继承 `journal_mode=WAL` | 读一次就生成 `-wal`/`-shm`，污染目录且让轮转漏删 | 备份后切 `PRAGMA journal_mode=DELETE`，并清理伴生文件 |
| Windows 上「关连接立刻删」失败 | 日志说清理了、文件还在（旧备份堆积占满磁盘） | 删除带 3 次重试，失败逐条告警而不静默吞掉 |

**自检不是"文件存在"，是"文件可用"**：跑 `PRAGMA integrity_check` 并与源库**逐表比对行数**。

⏱️ 实测（4 次连续备份，`--keep 2`）：轮转后目录恰好 2 个 `.db`、**零伴生文件**；备份独立打开可读，`users=21 / datasets=5 / tasks=57 / predictions=67574` 与源库一致。

**参数边界**：`--keep 0` → 退出码 2；源库不存在 → 退出码 1 并给出提示。

**文档**：手册 §7.1 已补用法、cron 与 Windows 计划任务示例、以及上面三个坑的说明（重新导出，31 页，TOC 已展开）；README 部署节加了两行；`backups/` 已加入 `.gitignore`。

### `Y-14` 守卫的「自证清白」—— ✅ 已关闭（2026-10-21）

原实现：缺 `pymupdf` 时跳过页数与目录检查，**结论行却照打印「目录已展开」** —— 等于给出了自己没验证过的断言。

改为按检查范围输出结论，并新增 `--strict`：

| 场景 | 结论文案 | 退出码 |
|---|---|---|
| 全绿（有 pymupdf） | 全部通过（齐备 · 新鲜 · 目录已展开） | 0 |
| 降级（缺 pymupdf） | 通过（齐备 · 新鲜）**⚠️ 未检页数与目录域** | 0 |
| 降级 + `--strict` | 同上 + `[STRICT] 已要求真检，但缺少 pymupdf —— 判定为未通过` | **2** |
| 有失败项 | N 项未通过 | 1 |

⏱️ 四种组合均实测通过。**验收/CI 应带 `--strict`**，避免"降级绿灯"被当成真检。
