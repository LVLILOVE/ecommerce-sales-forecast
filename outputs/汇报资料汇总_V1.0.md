## 二、项目背景

### 2.1 业务问题 → 可验收的硬指标

| 层 | 内容 |
|---|---|
| **业务问题** | 补货靠人工看 Excel；跨仓补货时不知道该看哪个仓；**长尾 SKU 历史不足却硬要一个数**，人拍脑袋填的数比不给数更危险 |
| **粒度决策** | 主粒度 = **仓库 × 商品**；**仓库列缺失即拒**（不猜、不补、不默认「华东仓」） |
| **稀疏数据对策** | 三级建模分级 + 三级降级：L1 直接建模 / L2 商品级外推 × 本仓占比 / L3 **不输出数值预测**，只给历史均值并标记不可预测 |
| **硬指标（PRD 定死）** | ① 加权 MAPE ≤ 20% ② MAE 优于移动平均基线 ≥ 15% ③ RMSE 优于基线 ≥ 15% ④ 达标序列占比 ≥ 60% ⑤ 端到端 ≤ 60 秒 |

> 🔴 **答辩最容易被问的点**：「为什么基线是移动平均而不是 LSTM 比 LSTM？」
> → 因为「比一个更笨的方法好多少」才是业务能用的结论；所以本项目**同时报 MAE/RMSE 与基线的对比**，而不是只报 MAPE。

## 五、关键数据（每条都可复现）

### 5.1 四条硬指标（**汇报的核心**）

| 指标 | 实测 | 红线 | 余量 | 出处 |
|---|---|---|---|---|
| **加权 MAPE** | **14.26%** | ≤ 20% | 优于 5.74 个百分点 | `outputs/eval_report.json` → `metrics.weighted_mape` |
| **MAE 相对基线** | **↓ 26.42%** | ≥ 15% | 超 11.42 个百分点 | 同上 → `metrics.mae_improve_pct` |
| **RMSE 相对基线** | **↓ 27.52%** | ≥ 15% | 超 12.52 个百分点 | 同上 → `metrics.rmse_improve_pct` |
| **达标序列占比** | **83.95%**（68/81） | ≥ 60% | 超 23.95 个百分点 | 同上 → `metrics.series_pass_rate` |

> 📌 **口径（必须主动讲，否则被追问会很难解释）**
>
> - **加权 MAPE 14.26%** = `Σ|e| / Σ|y|`，**全量 113 条序列**的总量视角。
> - **达标序列占比 83.95%** = **68 / 81**，⚠️ **分母是 L1 建模序列**，不是全部 113。
>   PRD 的这条指标针对「有资格被考核的建模序列」；L2 是降级结果、L3 无数值预测，
>   本就不该用同一个精度标尺考核。
> - **若把全部 113 条都算进去**，逐序列达标率是 **69 / 113 = 61.06%** —— **仍然高于 60% 的红线**。
> - **逐序列 MAPE**：中位数 **16.75%**、均值 28.35%、最大 86.88%。
>
> 🔴 **必须主动说的那个数字**：**L2 的 MAPE 是 60.33%**（L1 是 14.26%），
> L2 逐序列达标仅 **1 / 32（3.1%）**。
> 这不是 bug，而是「商品级外推 × 本仓占比」这个降级策略的**必然代价**。
> 讲法：「正因如此，我们坚持把 **L1/L2/L3 分开披露**、把 L3 标成不可预测，
> 而不是给降级序列硬凑一个漂亮的总数字。**指标好看不代表模型好，
> 把不可靠的部分标出来才是工程价值。**」

### 5.3 性能（60 秒硬约束）

> 🔴 **两个耗时不是一个数，别说混**：**算法层**两遍流水线 vs **端到端**任务耗时。
> 对用户承诺的 60 秒指的是**端到端**。

| 项 | 值 | 出处 |
|---|---|---|
| **端到端建任务**（113 序列 × h=14，本机 GPU） | **11,854.8 ms** | `ep9_perf_report.json` → `timings_ms.e2e_h14_sample_ms` |
| 算法层两遍流水线合计 | 7,873 ms | `eval_report.json` → `timing_ms.total_ms` |
| ├ 预处理 | 675 ms（另一次运行 786 ms） | 同上 `timing_ms` |
| ├ 特征构建 | 763 ms（另一次 1,100 ms） | 同上 |
| ├ **批量推理** | **21 ms**（另一次 14 ms） | 同上 |
| └ 指标计算 | 473 ms（另一次 636 ms） | 同上 |
| 推理占流水线比 | **0.27%**（21 / 7,873） | — ⇒ **性能瓶颈不在 GPU**，在数据处理与落库 |
| 端到端 SLA | 60,000 ms ⇒ **余量约 5 倍** | `ep9_perf_report.json` → `summary.sla_ms` |
| 性能用例 | **47/47** 通过 | 同上 `summary.passed` |
| **3 并发** | 墙钟 **37,657 ms**（单任务 32.2 / 37.6 / 37.5 s） | `timings_ms.concurrent3_*` |
| **超预算行为** | 施压至 **250,302 ms** → 触发 `E_TIMEOUT` **软失败**（不返 502/504） | `timings_ms` |
| 演示流程端到端 | **1,001.9 ms**（上传 87.8 + 建任务 h=7 838.7 + 结果 44.1 + 明细 18.7 + 导出 12.6） | `outputs/ep10_demo_report.json` |

> 📌 **容量结论（会被问「能扛多少并发」）**：单请求余量 5 倍，但 **3 并发就把耗时推到 32 s 以上**
> ⇒ 容量应按「**并发 ≤ 3**」设上限；并发失控时**宁可显式超时也不静默排队**
> （这正是 `E_TIMEOUT` 软失败机制存在的意义）。

### 6.1 已解决的技术难点（**讲这些，不讲踩坑流水账**）

| # | 难点 | 方案 | 可讲的证据 |
|---|---|---|---|
| **D-1** | **稀疏数据不能硬给数** | 三级分级 + L3 拒绝输出数值预测 + 覆盖率披露 | `FR-MOD-09` / `UX-AC-10`；L3 由 `verify_ep5_api`/`verify_ep6_api` 用构造低历史序列实测 |
| **D-2** | **60 秒预算形同虚设**（唯一检查点在流水线跑完后，最大负载能跑 213 秒） | 编排层 3 处 `deadline` 检查 → `E_TIMEOUT` 软失败 | 预算压到 1 ms ⇒ **324 ms 即在 `preprocess` 中断** |
| **D-3** | **登出后 Token 复活**（内存黑名单重启/多 worker 即失效） | 双轨撤销，均落库 | `revoked_tokens` 表（`DB-T09`） |
| **D-4** | **导出会把整表读进内存**（20 万行 38.8 MB） | 流式导出（峰值 6.1 MB） | `prepare_export` → `iter_export_chunks` |
| **D-5** | **CSV 公式注入**（下载即中招，受害者是业务人员） | 统一 `app/core/csv_safety.py`，数值列不转义 | `=cmd\|'/c calc'!A0` 专项守卫 |
| **D-6** | **模型文件被改动会让在线推理静默出错** | `model_registry` 唯一激活 + 权重哈希校验 | `DB-T06` |
| **D-7** | **埋点把 SQLite 写锁持有整个推理时长** | 写完立刻 commit（病根），`busy_timeout` 15 s（兜底） | 3 并发 `database is locked` → 修复后 3/3 成功 |
